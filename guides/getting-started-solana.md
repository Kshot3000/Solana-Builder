## 2. Set up a devnet wallet

```bash

solana-keygen new
solana airdrop 2
solana balance
```

Devnet SOL is free and worthless, on purpose: learn there, never on mainnet.

## 3. Learn the fifty-six mechanics that decide your costs

1. **Lamports.** 1 SOL = 1,000,000,000 lamports; balances are whole lamports. The hub's converter (Tool 1) shows the exact integer math.
2. **Rent exemption.** An account is rent-exempt holding two years of rent: `(128 + dataLen) × 3,480 × 2` lamports. A token account (165 bytes) therefore locks up 2,039,280 lamports — every account your program creates has a SOL cost you can compute before writing code (Tool 3).
3. **Pool pricing.** AMM swaps price off the constant-product curve. Run the swap model (Tool 2) at a few sizes and watch price impact: that curve is what Raydium, Orca and every aggregator route around.
4. **Transaction fees.** Every transaction pays 5,000 lamports per signature, plus an optional priority fee: `ceil(CU limit × CU price ÷ 1,000,000)` lamports, with the price in micro-lamports per compute unit. The fee is charged on the limit you request (capped at 1,400,000 CU), not the compute you use — simulate first and set the limit close to real usage. The hub's estimator (Tool 5) works the numbers.
5. **Token decimals.** Lamports are the 9-decimal special case: every SPL mint sets its own decimals (USDC 6, many mints 9, some 0), token accounts store raw integer amounts, and the UI amount is raw ÷ 10^decimals. Never hardcode 9 for a token — read the decimals off the mint, and reject amounts finer than they allow instead of rounding them. The hub's converter (Tool 6) shows both directions exactly.

6. **Address format.** An address is 32 bytes in base58 — the alphabet omits 0, O, I and l so addresses can't be misread, and leading `1`s are leading zero bytes (the System Program is 32 zero bytes). Anything that isn't base58, or decodes to anything but exactly 32 bytes, is not an address: a paste with two stray characters tacked on decodes to 33 bytes and fails. The hub's checker (Tool 7) validates the format locally — then still compare the full address character-for-character with its source, because format says nothing about whose address it is.

7. **Staking rewards.** Rewards are paid once per epoch — 432,000 slots, about 2 days at the target slot time, so about 182.5 epochs a year. A validator's commission is a percentage of the reward, not of the stake, and rewards credited to an active stake account compound from the next epoch on. Model it before you delegate (Tool 8): at an assumed 7.3% gross annual yield, one epoch pays 0.04% of the stake before commission. The yield is an assumption, never a live quote — real yield moves with inflation, total stake and validator performance, stake takes about an epoch to activate, and unstaking takes about an epoch to cool down.

8. **Payment links (Solana Pay).** A transfer request is one URL: `solana:<recipient>?amount=…&spl-token=…&reference=…&label=…&message=…&memo=…`. The recipient is a native account — associated token accounts must not be used as the recipient, because the wallet derives the token account from the `spl-token` mint. The amount is in user units (SOL, not lamports; a token's UI amount, not raw units): 0 is valid, a missing amount means the wallet asks the payer, decimals below 1 need a leading 0, scientific notation is prohibited, and an amount finer than the asset's decimals (9 for SOL, the mint's own otherwise) is malformed. Label and message are display-only; a memo goes on-chain in an SPL Memo instruction and is public forever. Reference is the one repeatable field — wallets attach the keys to the transfer in order, which is how a merchant finds a payment afterwards. The hub's builder and inspector (Tool 9) work both directions locally: build a link, then paste it back and read what it actually says before you share or pay it.

9. **CLMM ticks (concentrated liquidity).** On Raydium CLMM and Orca Whirlpools, prices live on ticks: `price(tick) = 1.0001^tick` — one tick is one basis point, and the on-chain range is −443,636 to 443,636. A position's endpoints must be aligned to the pool's tick spacing (`tick % spacing == 0`), and it is in range — active and earning fees — only while `tickLower ≤ tickCurrent < tickUpper`; at or above the upper tick it holds only one asset and earns nothing. Price-to-tick is a floor: the largest tick whose price is at or below the price you mean. The hub's converter and range checker (Tool 10) work both directions locally; prices there are in raw token units, so a UI price also needs the two mints' decimals.

10. **Slippage tolerance.** Every swap you sign carries a bound derived from a tolerance you pick: minimum received = expected out × (1 − tolerance) for an exact-in swap, maximum input = expected in × (1 + tolerance) for an exact-out swap, both floored in exact integer math so the bound is never looser than the tolerance — an expected 4 at 0.5% protects at 3.98, never rounded back up to 4. The program aborts rather than fill past the bound. Too tight (a few bps on a volatile pair) and ordinary movement fails the swap while the fee is still paid; too loose and a bad fill — or a sandwich attack — passes. The hub's calculator (Tool 11) works both bounds; a dust quote whose minimum floors to exactly 0 is flagged there as protecting nothing, because at that precision it doesn't.

11. **The epoch schedule (warmup is real).** An epoch is 432,000 slots only after the warmup: epoch 0 holds 32 slots and each early epoch doubles (32, 64, 128, …, 262,144 for epoch 13), so the first normal epoch is 14 and it starts at slot 524,256. The correct conversion past the warmup is `epoch = 14 + (slot − 524,256) ÷ 432,000`; the textbook `slot ÷ 432,000` calls slot 524,256 "epoch 1" and stays a dozen-plus epochs behind forever. Anything keyed to epoch boundaries — staking rewards, stake activation and cooldown, leader schedules — is mis-timed by code that divides naively. The hub's converter (Tool 12) implements the runtime's EpochSchedule in both directions. And never turn slots into wall-clock time with a fixed slot duration: the target was 400 ms for years and was cut in stages during 2026, and skipped slots stretch real epochs further — for an actual timestamp use `getBlockTime` or an explorer.

12. **Token-2022 transfer fees.** A mint created under the Token-2022 program can carry a TransferFeeConfig: on every transfer the sender is debited the full amount, the recipient is credited amount − fee, and the fee stays withheld in the recipient's token account until someone harvests it to the mint and the withdraw-withheld authority collects it. The program's fee is exact integer math on raw amounts: `fee = ceil(amount × basisPoints ÷ 10,000)`, capped at the mint's `maximumFee`, and 0 when the rate or the amount is 0 — so any positive transfer at a positive rate pays at least 1 raw unit, and a 1-unit transfer of a fee-bearing token delivers 0. The classic SPL Token program has no transfer fees at all, so which program a mint lives under changes what a payment delivers. A mint stores an older and a newer fee and picks by epoch; read the configuration that applies now. The hub's calculator (Tool 13) works the fee in both directions — including the gross-up: the smallest amount to send so the recipient receives an exact net (send 1,000,000 at 100 bps with a 5,000 maximum fee and the recipient receives exactly 995,000, the fee capped at 5,000).

13. **Sandwich attacks (MEV).** A swap that is visible before it lands can be sandwiched: the attacker buys the same direction first, pushing the pool price against the victim, lets the victim fill at the worse price, then sells back into the price the victim's own trade moved. The profit is not created — it is the victim's loss, minus the pool fees on the attacker's two legs. The defence is already in your transaction: the minimum-received bound from your slippage tolerance (item 10). Tight enough, and the sandwiched fill falls below the bound, so your transaction aborts instead of filling — you pay the network fee but lose nothing to the pool, and the attacker must unwind the front-run alone, paying the round-trip fees and price impact for nothing. Loose enough — a 20% tolerance on a volatile pair — and a fill 16% worse than the quote passes its own protection. Private transaction routing is the other defence: a swap nobody can see cannot be front-run. The hub's model (Tool 14) runs all three legs through the swap model of item 3 against the reserves each leg leaves, so you can watch the same inputs flip from extracted to protected as the tolerance tightens (at 100/100/100 with a 25 bps fee: loose 2,000 bps tolerance — victim loses 15.10132183 B, attacker profits 17.478992956 A; tight 50 bps — victim aborts, attacker loses 0.454183462 A unwinding).

14. **Liquid staking exchange rates.** A liquid staking token is a share of a pool, not a balance that grows: the pool's staked SOL total rises as rewards land, the token supply does not move, and the exchange rate — total ÷ supply, in SOL per token — carries all of the yield. Deposits mint `deposit × supply ÷ total` tokens and redemptions return `redeem × total ÷ supply` SOL, floored like the on-chain integer division, so a dust deposit at a high rate can mint zero tokens. Two consequences follow for anyone building on LSTs: never hard-code 1 token = 1 SOL (a mature pool's rate is above 1 and drifts up every epoch), and never quote a redemption from a stale rate. Real pools also charge deposit, withdrawal or epoch fees and an unstake that pool liquidity cannot cover waits out the deactivation cooldown — neither is in the hub's model (Tool 15), which prices the pure rate: at 1,100 SOL backing 1,000 tokens the rate is 1.1, a 110 SOL deposit mints exactly 100 tokens and 100 tokens redeem for 110 SOL; after 55 SOL of rewards the rate is 1.155 and the same redemption returns 115.5 SOL.

15. **Program-derived addresses (PDAs).** A program holds state and signs without any private key through addresses derived — not generated — as `SHA-256(seeds ‖ bump ‖ programId ‖ "ProgramDerivedAddress")`, kept only when the hash is NOT a valid ed25519 point: an on-curve address could have a private key, so it can never be a PDA. The search starts at bump 255 and steps down; about half of all hashes are off-curve, so it usually lands within a couple of tries, and the bump that worked is stored and passed back as the final seed whenever the program signs with `invoke_signed` — anyone can re-derive the address from the same seeds, which is the point: the address is verifiable, not registered anywhere. The rules are at most 16 seeds, each at most 32 bytes; seeds are raw bytes (text means its UTF-8 encoding, so a 33-character seed fails on bytes, not characters — and a multi-byte character counts for more than one). The derivation you will meet most is the associated token account: the ATA program deriving from `[wallet bytes, token program bytes, mint bytes]`. The hub's finder (Tool 16) runs the whole derivation locally — its own SHA-256 plus the ed25519 curve check — and was cross-verified against the reference SDKs: the seed `vault` under the SPL Token program (`TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA`) derives `AispKP3Ls5d2m6t411kMtP1xkPemdZPGPJUvemsBqmXA` at bump 254 (its bump-255 candidate lands on the curve and is skipped), and the hub's own donation wallet's USDC associated token account derives to `BeJv9nhxhAhGVUpVaN4USa9TgpGiYhauc6VU5QyQZrbq`. Derivation being pure hashing cuts both ways: the same program and seeds always give the same address on every cluster — and a plausible-looking "program account" from a stranger is worth nothing until you have re-derived it from the program ID and seeds you trust, in full.

16. **CLMM position amounts.** A concentrated-liquidity position is defined by a liquidity amount L and a tick range — not by token amounts, which are derived from the square-root prices (price = token1 per token0, item 9): inside the range, `amount0 = L × (1/√P_current − 1/√P_upper)` and `amount1 = L × (√P_current − √P_lower)`; at or below the lower tick the position holds only token0 (`L × (1/√P_lower − 1/√P_upper)`), at or above the upper tick only token1 (`L × (√P_upper − √P_lower)`), and the two branches meet the inside formulas exactly at the boundaries, so the composition slides continuously from one asset to the other as price crosses the range. That slide is the position's whole risk shape: it sells the appreciating asset into the depreciating one the entire way across, which is where impermanent loss comes from. The amounts are principal at the current tick only — swap fees the position earns accrue into separate fee balances on-chain, and withdrawing after a price move returns a different split than depositing did. The hub's calculator (Tool 17) works the three branches locally and was cross-verified against a reference SDK's integer (Q96) implementation: L = 1,000,000 over ticks −600…600 holds 60,005.999… of token0 alone at or below tick −600, about 29,553.011 of each at tick 0, and 60,005.999… of token1 alone at or above tick 600.

17. **LP deposits and pool share.** Adding liquidity to a constant-product pool (item 3) mints LP tokens from the smaller side's contribution: `minted = supply × min(depositA ÷ reserveA, depositB ÷ reserveB)`, each division floored like the on-chain integer math. Only the part of the deposit matching the pool's current ratio is used — deposit 10,000 A / 50,000 B into a 1,000,000 A / 4,000,000 B pool with 2,000,000 LP tokens outstanding and token A limits the mint at 20,000 LP tokens: 40,000 of the B is used, 10,000 B is excess that buys nothing, and the depositor holds 20,000 ÷ 2,020,000 ≈ 0.990099% of the pool. An exact-ratio deposit (10,000 / 40,000 there) mints the same 20,000 with no excess. The first deposit into an empty pool has no ratio to match: it sets the starting price and mints the geometric mean `sqrt(depositA × depositB)` — some pools permanently lock a small minimum of that first mint as a defence against share-inflation attacks, a pool-specific detail this model states but does not apply. Burning LP tokens later returns your share of whatever reserves the pool holds at that moment, which after trading fees and price moves is a different amount and a different split than went in — that difference is where impermanent loss (and fee earnings) live. The hub's calculator (Tool 18) works both branches in exact integer math, including the integer square root.
18. **Token vesting.** Team, investor and ecosystem allocations commonly vest cliff + linear: the allocation accrues linearly over the full duration from day one — `accrued = total × min(elapsed, duration) ÷ duration`, floored at the token's smallest unit — but nothing is claimable before the cliff month, when the whole accrued share releases at once and claimable follows accrual from then on. A 1,000,000-token allocation with a 12-month cliff over 48 months has accrued 125,000 at month 6 with exactly 0 claimable, releases 250,000 at the cliff, and stands at 375,000 claimable (37.5%) by month 18, completing at month 48. Two reading rules: value a locked allocation by its claimable figure, never its accrued one; and check the convention — a minority of schedules start the linear accrual AT the cliff instead of gating it, and real contracts run on timestamps (per second or per slot), not whole months. The hub's calculator (Tool 19) works the gated-accrual model in whole months in exact integer math.


19. **Lending health.** A lending market (Kamino, Marginfi, Drift) tracks collateral value = amount x price, loan-to-value = debt / value, and a health factor = (value x liquidation threshold) / debt: below 1 the position may be liquidated. The price where health equals 1 is the liquidation price, debt / (amount x threshold) - 10 tokens at a price of 100 against 500 of debt at an 80% threshold gives a health factor of 1.6 and a liquidation price of 62.5. Borrowing power is set by the lower max LTV (75% there: a max borrow total of 750), and the gap between max LTV and threshold is the safety buffer. Interest accrues continuously in a real market, so a real health factor drifts even at a flat price - the hub's calculator (Tool 20) models the flat-price snapshot in exact integer math.

20. **Transaction size.** A transaction must fit one network packet - 1,232 bytes - and its serialized size is exact: a shortvec count plus 64 bytes per signature, a 3-byte header, a shortvec plus 32 bytes per static account key, a 32-byte blockhash, and per instruction a program-index byte, two shortvec counts, one byte per referenced account and the data itself (a shortvec length is 1 byte below 128, 2 below 16,384). A plain SOL transfer - 1 signature, 3 keys, 2 instruction accounts, 12 data bytes - is exactly 215 bytes. Versioned (v0) transactions load accounts through address lookup tables at a 1-byte index each instead of 32 bytes, which is how complex DeFi transactions fit at all - but the table reference costs 32 bytes plus two shortvec counts first, so a table holding one referenced account makes a transaction 4 bytes bigger, while the same transfer with its two non-payer keys in one table is 188 bytes and saves 27. Legacy transactions reference at most 256 accounts (u8 indices); tables lift that ceiling by up to 256 addresses per table. The hub's calculator (Tool 21) measures one instruction with an optional single table in exact byte math.

21. **Account space (Anchor/Borsh).** An Anchor account is 8 discriminator bytes plus its fields at Borsh sizes, packed back to back with no padding or alignment: bool/u8 1 byte, u16 2, u32 4, u64 8, u128 16, Pubkey 32; a String or Vec<u8> costs a 4-byte length prefix plus its declared capacity, a Vec<T> 4 + count x size(T), an array [T; N] N x size(T), an Option<T> 1 tag byte + size(T), and an enum 1 + its largest variant. The total is not bookkeeping - it IS the rent-exempt deposit of item 2: a vault struct of Pubkey + u64 + bool + String(32) is 8 + 32 + 8 + 1 + 36 = 85 bytes and locks 1,482,480 lamports. Over-allocating wastes that deposit permanently (realloc exists, but the habit costs on every account); under-allocating fails the first write that outgrows the space. The hub's planner (Tool 22) sizes up to four fields and prices the total with the rent formula; larger structs add linearly, and enums are added by hand at 1 + largest variant.

22. **Sale splits (marketplace fees and royalties).** A marketplace sale or escrow release splits one price three ways: a platform fee in basis points, a creator royalty in basis points, and the seller's remainder. Both cuts floor at the smallest unit like on-chain integer math — `fee = price × bps ÷ 10,000` floored — and the seller receives `price − fee − royalty`, never a third independently rounded percentage, so the three parts sum to the price exactly and the seller keeps the flooring dust: a sale at 100 with a 200 bps platform fee and a 500 bps royalty pays 2 to the platform, 5 to the creator and 93 to the seller, while a 3-unit price split 50/50 pays 1 unit to each cut and 1 unit to the seller. Rates summing past 10,000 bps would pay the seller a negative share and are rejected; summing to exactly 10,000 can leave the seller exactly 0. Two scope notes: this model takes both cuts out of the price (some venues charge the buyer on top instead), and creator royalties on classic Solana NFTs are a marketplace convention — programmable NFTs can enforce them on-chain, classic ones rely on the venue honouring them. The hub's calculator (Tool 23) works the split in exact integer math.

23. **Stake warmup and cooldown.** Delegated stake changes state only at epoch boundaries, and only a rate-limited share of the cluster may move per epoch: an account's allowed change is its portion / the total moving the same way x the cluster's previous-epoch effective stake x the warmup/cooldown rate, floored, clamped to its own portion, with a minimum progress of 1 lamport per epoch. The rate is 900 bps (9%) on the current network - it was 2,500 bps (25%) before the reduce_stake_warmup_cooldown feature - so at most 9% of the cluster's effective stake activates or deactivates per epoch, shared pro-rata by everything in the queue. A stake small against the cluster is fully effective after one epoch; a whale-sized move queues: 40,000,000 SOL activating solo against a 400,000,000 SOL cluster moves 36,000,000 in epoch 1 and the remaining 4,000,000 in epoch 2, and a crowd unstaking together divides the same cap by share, which is why a deactivation can still be draining after an epoch rolls. The hub's timer (Tool 24) runs the formula epoch by epoch in exact integer math, holding the cluster's effective stake constant at your figure and assuming other movers drain at the same fractional pace.

24. **CLMM fee growth (uncollected fees).** A concentrated-liquidity position stores no running fees total. The pool keeps fee-growth counters - fees per unit of liquidity in X64 fixed point (scaled by 2^64), stored as u128 integers: a global counter per token, an outside counter per tick, and inside each position the fee growth inside its range at its last touch. The growth inside is global - below(lower) - above(upper), and the fees earned since the last touch are floor((inside now - inside last) x liquidity / 2^64), added to whatever an earlier touch already settled into the position's tokens-owed balance. The subtraction wraps modulo 2^128, exactly like the on-chain u128 arithmetic: a current counter lower than the stored one is the counter wrapping, not negative fees, and the delta is still the true increment. Touching a position (adding or removing liquidity, collecting) settles the accrued fees and re-stores the counter, which is why the growth delta only ever describes the span since the last touch - older fees live in the owed figure, never in the delta. At liquidity 1,000,000, growth up exactly 2^64 (1.0 per unit of liquidity) accrues exactly 1,000,000 raw units. The hub's calculator (Tool 25) runs this in exact BigInt on the raw integer counters, which are far beyond float range; the counters themselves are inputs, as an explorer or the SDK reports them.

25. **The inflation schedule (new SOL issuance).** SOL has no supply cap: every epoch mints new SOL as staking rewards at a rate set by three parameters in the validator code - an initial rate of 8% per year, a disinflation rate of 15% per year, and a long-term terminal rate of 1.5% the schedule never falls below: rate = max(1.5%, 8% x (1 - disinflation)^years). The year is fractional on-chain - the validator recomputes the rate every epoch from the fraction of a year elapsed since inflation began at epoch 150 (February 2021) - so the rate glides down continuously rather than stepping once a year: year 1 is 6.8%, year 5 is 3.5496%, and the terminal floor arrives at year ~10.30 (the first whole year at 1.5% is year 11). Annual issuance is the rate x the total supply; at year 5 on a 500,000,000 SOL supply that is 17,748,212.5 new SOL, paid to validators and their delegators - which is why a non-staker's share of the supply shrinks even though their balance never changes. Governance adopted doubling the disinflation rate to 30% in 2026 (the floor would arrive at year ~4.69 instead), but it is not implemented in the validator yet, so 15% remains the shipped schedule - model the 30% path, never quote it as current. The hub's calculator (Tool 26) runs the schedule with the supply held at your figure; on-chain the supply itself grows by each year's issuance.

26. **Associated token accounts (ATAs).** Almost every token balance on Solana lives in an associated token account: one canonical token account per (owner, mint) pair whose address is a program-derived address under the Associated Token Account program, derived from the seeds [owner, token program, mint] in exactly that order - which is why any wallet or app can recompute your token account address from your wallet and the mint alone, and why sending to a wallet "just works" once the ATA is created. The token program seed matters: the same wallet and mint have different ATAs under the classic SPL Token program and under Token-2022, and they are different accounts on-chain. The owner may itself be a PDA - programs custody tokens through ATAs owned by PDAs all over the ecosystem. Worked example: the hub's donation address G7xepVyQSrxtH61ZooXvPAmnS8omQ1TvHqB8qDmHXWm holding the USDC mint EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v under the classic token program has the ATA BeJv9nhxhAhGVUpVaN4USa9TgpGiYhauc6VU5QyQZrbq (bump 255, the first candidate tried). The hub's finder (Tool 27) runs the derivation on the same SHA-256 + ed25519 curve-check engine as its general PDA tool; the derivation is pure math - whether the account has been created on-chain yet (creating it costs rent, usually paid by the sender of a first transfer) is a separate question the tool does not read.

27. **Compressed NFT trees (state compression).** A compressed NFT keeps no per-asset accounts on-chain: the assets live in an off-chain indexer, and the only on-chain state is one concurrent Merkle tree account under SPL account compression (the structure Metaplex Bubblegum mints into). Its size is fixed at creation by three choices: account bytes = 56 (header) + 64 (counters and rightmost-path fixed data) + bufferSize x (40 + 32 x maxDepth) for the changelog ring + 32 x maxDepth of rightmost proof + (2^(canopyDepth+1) - 2) x 32 of canopy, if any. The changelog ring - one entry per recent change, each a root, an index and one hash per tree level - is what lets many mints update the tree concurrently, and it is almost the entire account: a depth-14, buffer-64, no-canopy tree is a 31,800-byte account (31,232 of those bytes are the ring) whose rent-exempt deposit is 222,218,880 lamports (0.22221888 SOL), for a capacity of 2^14 = 16,384 assets - about 13,563 lamports of tree rent per asset at full capacity, against a whole token account's rent for every single uncompressed NFT. Depth sets capacity (2^maxDepth leaves), the buffer must be a power of two (the ring is indexed by mask) and sets how many in-flight updates the tree absorbs before proofs go stale, and a canopy stores the top levels on-chain so every later transfer supplies depth - canopyDepth proof hashes instead of depth; past depth 17, Bubblegum's tree creation requires a canopy of at least maxDepth - 17. The compression whitepaper's depth-24, buffer-1024 tree makes the point at scale: 827,392 changelog bytes of an 828,280-byte account. The hub's planner (Tool 28) runs the layout; creating the tree also pays a normal transaction fee and minting into it is a separate cost, neither modelled there.

28. **Seeded addresses (createWithSeed).** Solana's other deterministic address predates the PDA: the system program's create_account_with_seed derives an account address as `SHA-256(base ‖ seed ‖ owner)` — the base signer's bytes, a single seed string, and the bytes of the program that will own the account. There is no "ProgramDerivedAddress" marker, no bump byte and no ed25519 curve check, so a result that lands on the curve is still a valid seeded address — nobody could know a private key for it, because the bytes are a hash output, and the account is controlled by its owner program after the base signs its creation. That is how the Solana CLI fans one keypair out into many stake accounts (`solana create-address-with-seed --from <base> 0 STAKE`, then seed "1", "2", … under the Stake program `Stake11111111111111111111111111111111111111`): this hub's donation address as base with seed "0" under the Stake program derives `4z22cSCVREYe519iEet4xdqBSrTDx9muhtRR3fcRxpod`, an on-curve result a PDA search would have rejected. Choose by who must sign: a PDA (item 15) when a program must sign with no key; a seeded address when a base keypair creates a family of accounts and signs their creation itself. The seed is at most 32 bytes as UTF-8 and is used byte-for-byte — it is never trimmed, so a seed with a stray space is a different account. The hub's finder (Tool 29) runs the derivation locally; whether the account exists on-chain is a separate question it does not read.
29. **Market cap and FDV (token valuation).** A token's headline valuation depends on which supply it multiplies by the price: market cap = price × circulating supply (what trades today), total valuation = price × total supply (everything minted so far), and the fully diluted valuation FDV = price × max supply (the cap, if every token existed). The minted-but-not-circulating gap (total − circulating) is the unlock overhang — locked, treasury and still-vesting tokens (item 18) — and max − total is not yet minted at all. The FDV ÷ market cap multiple is max ÷ circulating: the price cancels, so the multiple is a pure supply ratio measuring dilution still to come, not a price signal — and FDV quietly assumes today's price survives all that supply arriving. At a price of 2.5 with 400,000,000 circulating, 800,000,000 total and a 1,000,000,000 max, the market cap is 1,000,000,000, the total valuation 2,000,000,000 and the FDV 2,500,000,000 — 2.5× the market cap with only 40% of the max supply circulating. A token whose circulating supply equals its max is fully diluted and the three figures coincide. The hub's calculator (Tool 30) runs all three in exact integer math, with the two gap values taken as differences so the parts sum exactly to the FDV; the price and supplies are inputs — no live price or mint is read, and each data site's circulating figure is its own accounting of locked wallets.

30. **Address lookup tables.** A lookup table is an on-chain account a v0 transaction loads accounts through, paying a 1-byte index per account instead of a 32-byte key. Its layout is fixed: 56 bytes of metadata (deactivation slot, last-extended slot, authority) + 32 bytes per stored address, at most 256 addresses because the indexes are u8 — and it is priced like every account by the rent formula of item 2: a table storing 64 addresses is a 2,104-byte account locking 15,534,720 lamports, each stored address adding exactly 222,720 lamports, and a full 256-address table is 8,248 bytes and 58,296,960 lamports. In a transaction the lookup section costs a 1-byte list count, the table's own 32-byte key, two shortvec counts and 1 byte per loaded address — the same lookup figure as item 20 — so loading one address through a table makes that transaction 4 bytes bigger, not smaller; loading 20 (12 writable, 8 readonly) costs 55 bytes against 640 inline, saving 585 bytes in every transaction that loads them, which is why routers keep shared tables of pool and mint addresses. The deposit is not gone while the table lives, but reclaiming it is deliberately slow: deactivate, then wait until the deactivation slot is no longer recent in the SlotHashes sysvar before closing — the cooldown stops in-flight transactions being censored by a table vanishing under them. The hub's planner (Tool 31) runs the layout, the deposit and the per-transaction saving in exact integer math; several tables per transaction and the create/extend transaction fees are stated there as not modelled.

31. **Oracle price confidence (price ± conf).** Every price a Solana DeFi program acts on arrives as a band, not a point: a Pyth-style feed publishes three integers — price, conf and expo — meaning price × 10^expo, plus-or-minus conf × 10^expo, where conf is roughly one standard deviation of the publishers' aggregate estimate (the true price is expected inside the band about 68% of the time; a doubled band is roughly 95% only under a normal-distribution assumption, which is an approximation, not a promise). What decides whether a price is usable is the band's WIDTH relative to the price: 150.00 ± 0.075 is 5 bps wide and comfortably tradeable, while the often-quoted 67,890 ± 680 is 100.16 bps wide — it fails a strict 100 bps (1%) guard by a hair, and lending programs do exactly this check (`conf × 10,000 > price × guard` → reject) before a volatile minute can be borrowed or liquidated against. Cautious consumers also value collateral at the band's LOW end, so a widening band mechanically tightens positions before any price move does. The feed's other defence is staleness — rejecting a price whose publish time is older than a maximum age — which is a separate check this mechanic does not replace. The hub's interpreter (Tool 32) runs the band, the width and the guard in exact integer math on the raw feed values; the values are inputs, as an SDK or explorer reports them — no live feed is read.

32. **Bonding curves (launchpad pricing).** A token launched on a Solana launchpad does not start in a pool anyone funded: a program prices every trade off a constant-product curve over virtual reserves — a virtual SOL reserve and a virtual token reserve whose ratio is the price (`price = virtual SOL ÷ virtual token`) and whose product never changes. The word virtual matters: the SOL side is a pricing offset that sets the starting price and the curve's steepness, not a balance — the SOL the curve actually holds is the separate real figure buyers have paid in, and confusing the two misreads both the price and the funds available at migration. A buy pays the venue's fee on the input first (each venue sets its own), then receives `effIn × virtualToken ÷ (virtualSol + effIn)` tokens, floored — Tool 2's swap math against the virtual reserves — so every buy raises the virtual SOL reserve, drains the virtual token reserve and moves the price up the curve, and a sell runs the same math in reverse. At the headline curve (30 virtual SOL, 1,000,000,000 virtual tokens, 42 of an 85 SOL target already raised) a 3 SOL buy at a 100 bps fee receives 90,081,892.62966333 tokens and lifts the price 20.78%, from 0.00000003 to 0.000000036 SOL, taking progress to 52.9059% of graduation. Progress is measured on the real raised SOL: when it reaches the venue's target the curve completes (graduates) and the real SOL plus the unsold tokens migrate to a real AMM pool — Raydium, the venue's own AMM or a LaunchLab pool — usually calibrated so the first AMM price equals the curve's last price, while the depth drops because the virtual offset does not migrate, which is why a sell right after graduation absorbs worse than the same sell right before it. The market cap a launchpad interface quotes is just the curve price × the total supply — a product of the curve's current position, not a valuation. The hub's model (Tool 33) runs one buy in exact scaled-integer math, with the fee rate, reserves, raised figure and target all as inputs; no live curve is read.

33. **Perpetual funding payments.** A perpetual future never expires, so a periodic funding payment anchors its price to the spot/index price: the payment is `notional x rate x time`, where the notional is the position size x the mark price and the rate is quoted in basis points per hour (1 bp = 0.01% per hour). The sign carries the direction: at a positive rate longs pay shorts, at a negative rate shorts pay longs, and at exactly zero nobody pays. The amounts are not small just because the rate looks small: a 100-unit long at a mark price of 150 is a 15,000 notional, so at 1 bp per hour the long pays 1.5 per hour and 36 over 24 hours, and that hourly rate annualises to 87.6% (rate x 8,760 hours) as a quoting convention - not a forecast, because every venue resets its rate each interval from the mark/index premium, caps it at its own maximum and settles at its own interval (hourly is the common Solana cadence on venues like Drift and Jupiter Perps). Funding is a carry cost (or income) on top of price movement and fees: a position held for days can pay more in funding than its entry fee, which is why leveraged holds are judged on the rate as well as the entry. The hub's model (Tool 34) runs the payment in exact scaled-integer math from the position's point of view (negative pays, positive receives), with the size, mark price, signed rate and hours all as inputs; no live market is read.

34. **Lending interest rates (the kinked curve).** A Solana lending market prices a borrow off its utilization - total borrowed divided by total supplied - on a two-piece curve quoted as an annual rate in basis points: below the market's optimal utilization the rate is `base + slope1 x (U / Uopt)`, and above it `base + slope1 + slope2 x (U - Uopt) / (1 - Uopt)`. The first slope is gentle on purpose - borrowing is cheap while liquidity is plentiful - and the second is steep on purpose: as a market approaches full utilization there is almost nothing left to borrow, so the rate spikes to pull new deposits in and push borrows down before the market runs dry. Suppliers are paid out of that same interest: the supply rate is the borrow rate x utilization x (1 - reserve factor), because only the borrowed share of the pool earns anything and the protocol keeps the reserve factor of it - which is why a supply yield collapses when utilization falls away, even though the borrow rate printed on the curve has barely moved. The headline market (1,000,000 supplied, 800,000 borrowed, an 80% kink, 200 bps base, 400 bps first slope, 6,000 bps second slope, 1,000 bps reserve factor) sits exactly on its kink: the borrow rate is 600 bps (6%), suppliers earn 432 bps (4.32%), and the borrowed total accrues 49,465.048542105 of interest over 365 days. Raise the borrowed total to 900,000 - 90% utilization, ten points past the kink - and the second slope alone adds 3,000 bps: the borrow rate is 36% and suppliers earn 29.16%. Every parameter on the curve is set per market and changed by governance, real markets accrue interest continuously or per-slot rather than in daily steps, and their rates move as utilization moves - the hub's model (Tool 35) freezes utilization and compounds daily as a stated convention, runs the curve in exact scaled-integer math, and reads no live market.

35. **Perpetual position margin and liquidation.** A perpetual position is judged on its margin, not its size: post initial margin = notional / leverage, and the position's equity - margin + unrealised PnL, where PnL is (mark - entry) x size for a long and mirrored for a short - is liquidated when it falls to the maintenance margin, a venue-set rate (often tiered by size) times the CURRENT notional. Solving equity = maintenance for the price gives the liquidation price: for a long, (notional - margin) / (size x (1 - mmr)); for a short, (notional + margin) / (size x (1 + mmr)). Because the maintenance margin is a live share of the current notional, liquidation strikes while equity still remains - well before the margin reaches zero: a 100-unit long at 150, 10x leverage and a 500 bps maintenance rate posts 1,500 of margin and liquidates at 142.105263157, a fall of only about 5.26%, even though the margin alone would last to 135. The same leverage that sets the margin multiplies the return on it exactly: at a mark of 180 that position's PnL is 3,000, which is +200% on its margin for a +20% price move - and a symmetric fall is a symmetric loss. A long at leverage 1 or below has no liquidation price at all, because its margin covers the whole notional and the price cannot fall below zero. Funding (item 33) is a separate carry charged on top of this, and real venues also apply trading fees, partial liquidations and liquidation penalties this model states but does not include. The hub's calculator (Tool 36) runs the isolated-margin model in exact scaled-integer math, with the maintenance rate as an input; no live market is read.

36. **Stableswap pricing.** A pool of like-valued tokens - USDC against USDT - should not pay the constant-product curve's price impact for a trade its tokens are meant to clear at 1:1, so stable pools (Saber on Solana, Curve's design) price off a different invariant: `Ann x (x + y) + D = Ann x D + D^3 / (4xy)`, where Ann = A x n^n for n coins and A is the amplification coefficient. D is the pool's total value at the peg - for a balanced pool it equals the sum of the balances exactly. As A grows, the curve flattens toward a constant-sum line and prices hold at 1:1 near balance; as A falls toward 1, or the pool unbalances, it bends back toward constant-product pricing. Neither D nor the post-trade balance has a usable closed form, so both are solved by Newton iteration in integer math - the same method the on-chain programs run, good to a few smallest units on extreme inputs. The numbers: a balanced 1,000,000 / 1,000,000 pool at A = 100 has D = 2,000,000 and returns a 10,000 trade at 9,999.502463058 gross - a price impact under 0.005%, against the 9,900 the constant-product curve of item 2 returns - and after a 4 bps fee charged on the output the trader receives 9,995.502662073. Unbalance the pool to 1,500,000 / 500,000 and the same trade returns 9,910.453997586 gross: the curve defends the peg only while balanced liquidity backs it, and at A = 1 even a balanced pool returns only 9,966.775941841. The hub's calculator (Tool 37) runs the two-coin model in exact scaled-integer math with A and the fee as inputs; multi-coin pools and LP-token virtual-price growth are stated as not modelled, and no live pool is read.

37. **Liquidation proceeds.** Being liquidatable (item 19's health factor) is only half the lending mechanic — the other half is what one liquidation does. A market caps a single liquidation's repay at a CLOSE FACTOR share of the debt, and lets the liquidator seize collateral worth the repaid amount marked up by the LIQUIDATION BONUS: seized value = repay x (1 + bonus), seized amount = seized value / collateral price, floored in exact integer math. The bonus is the liquidator's profit and the borrower's extra loss, which is why borrowers watch the health factor, not just the liquidation price. The numbers: 10 units at 100 against a debt of 500, at a 500 bps bonus and a 5,000 bps close factor, repays 250 and seizes 2.625 units (worth 262.5, a bonus profit of 12.5), leaving 250 of debt against 7.375 units. If the marked-up seizure would take more collateral than the position holds, the collateral is exhausted instead: the liquidator takes all of it, the effective repay falls to collateral value / (1 + bonus), and the remaining debt is left with no backing — with only 2 units against that 500 debt the repay falls to 190.476190476 and 309.523809524 is left unbacked, the shortfall a market's insurance fund or socialised loss absorbs. Every market sets its own bonus and close factor, and some allow a full close once health is low enough (a 10,000 bps close factor here). The hub's calculator (Tool 38) runs the maximum single liquidation in exact scaled-integer math; interest accrual, liquidation fees and partial-liquidation sequencing are stated as not modelled, and no live market is read.

38. **Routed swaps.** A trade on Solana rarely goes through one pool: an aggregator (Jupiter, or a DEX router) routes A -> M -> B through two pools - into an intermediate token, usually SOL or a stablecoin, then onward - when no deep direct A/B pool exists or the routed price beats the direct one. Each hop is the constant-product swap of item 2 with its own fee charged on its own input, and the FULL intermediate amount is swapped onward, so the two fees and the two price impacts compound rather than add. The honest yardstick is the route's spot value - amount in x (mid reserve / in reserve) x (out reserve / mid reserve), what the trade is worth at quoted prices before any fee or impact. The numbers: pools of 500,000 / 75,000,000 and 30,000,000 / 600,000, both at 25 bps, turn 100 in into 14,959.515576642 of the intermediate and 298.293963175 out, against a spot value of exactly 300 - a total cost of about 0.57%. Zero the fees and the route still returns only 299.790146897: the two impacts alone compound. Shallow the second pool tenfold (3,000,000 / 60,000, same prices) and the return falls to 296.965219193 - the second hop's depth matters as much as the first's, which is why aggregators compare many routes instead of assuming one. The hub's calculator (Tool 39) composes its own swap model across both hops in exact scaled-integer math and reports that total cost in basis points; longer routes, split routes, concentrated-liquidity hops and any interface fee on top are stated as not modelled, and no live pool is read.

39. **Exact-out swaps.** Half of real swap demand fixes the OUTPUT, not the input: a payment, an invoice, a debt repayment or the second leg of an arbitrage must receive an exact amount, and the question is what it costs. A constant-product pool answers it backwards: the net input the pool must receive is `amountOut x reserveIn / (reserveOut - amountOut)`, ceilinged at the smallest unit, and the gross input is the smallest amount whose fee withholding (charged on the input, floored) still leaves that net - slightly more than a plain gross-up of the net, because the withholding itself floors. The headline pool (1,000,000 / 1,000,000 at 25 bps) delivers exactly 100,000 out for 111,389.585073796 in: the spot value of the output is 100,000, so the fee of 278.473962684 and the price impact take the other 11,389.585073796. Two honest edges define the mechanic: the denominator is the reserve MINUS the target, so the cost grows without bound as the target approaches the whole output reserve - receiving 999 of a 1,000 / 1,000 pool costs 1,001,503.759398496 in - and a target at or beyond that reserve can never be paid out at any price, which is why exact-out quotes against shallow pools look extortionate rather than merely expensive. And because every step floors, the smallest input that reaches a target can deliver a few smallest units MORE than it - a real exact-out fill keeps or returns that dust, it never vanishes. The hub's model (Tool 40) solves the input in exact scaled-integer math and reports its figures from the hub's own Tool 2 swap run at the solved input, so the two tools cannot disagree; CLMM exact-out (which walks ticks) and any interface fee are stated as not modelled, and no live pool is read.

40. **Arbitrage (how a pool learns the outside price).** A constant-product pool prices only from its own reserves, so when the same token trades elsewhere at a different price the pool is stale until someone trades it back into line: an arbitrageur buys the token the pool prices too cheaply, resells it at the external price, and keeps the gap minus the pool fee and the price impact - and the trade itself moves the pool's price, which is what closes the gap for everyone else. Size is the whole mechanic: against a 1,000,000 / 1,000,000 pool (spot 1) with the output worth 1.21 elsewhere, a 100,000 trade at no fee receives 90,909.09090909, worth 109,999.999999998 - a profit of 9,999.999999998, two smallest units short of the textbook 10,000 because each floored step costs dust - and leaves the spot at 1.209999999, aligned; double it to 200,000 and the profit collapses to 1,666.666666665, because past alignment every further unit buys dearer than it resells. A fee shrinks the exploitable gap from both ends: at 25 bps the same trade profits 9,749.943168901 and stops at a spot of 1.209450062, so a gap smaller than the fee plus impact is no gap at all. The hub's model (Tool 41) runs the swap through Tool 2 itself and values the output at a user-quoted external price in exact scaled-integer math; the external sale is assumed to fill in full at that price - external fees, slippage and transaction costs are stated as not modelled - and no live price or pool is read.

41. **CLMM swaps (trading inside one tick range).** A concentrated-liquidity swap does not trade against the tokens a pool holds - it trades against the active liquidity L of the tick range the price is currently in, moving the square-root price: paying token0 sets `1/√P_new = 1/√P_now + effectiveIn ÷ L` and pays out `L × (√P_now − √P_new)` of token1, and paying token1 sets `√P_new = √P_now + effectiveIn ÷ L` and pays `L × (1/√P_now − 1/√P_new)` of token0, with the pool fee withheld from the gross input first. Inside the range this is exactly a constant-product swap on the range's virtual reserves (`L ÷ √P` and `L × √P`): at price 1 with L = 1,000,000 those reserves are 1,000,000 each, so a 10,000 trade at 25 bps returns 9,876.482091141 - Tool 2's own figure for a 1,000,000 / 1,000,000 pool - and at no fee it returns 9,900.99009901 and moves the price to 0.9802960494. The range is also the trade's limit: in a −100…100 range only 5,012.269623051 of that 10,000 fits before the price reaches the bound (paying 4,987.272070749), and on-chain the remainder crosses into the next tick range against whatever liquidity is active there - different depth, different price - which is why a CLMM quote for a large trade is a walk across ranges, not one formula. The hub's model (Tool 42) works one range in floating point (on-chain the square-root price is Q64.64 fixed point), stops at the bound and reports the unused input rather than inventing the next range's liquidity; tick crossing and interface fees are stated as not modelled, and no live pool is read.

42. **Walking a limit-order book.** Not every Solana market is a pool: central limit order books (Phoenix, OpenBook, Manifest) hold resting limit orders, each at its maker's own price, and a market buy fills against the ask side in price order - best (lowest) ask first, then the next - paying each level's own price, never an average the book did not offer. The fill's honest summary is its volume-weighted average price, VWAP = total cost divided by filled quantity, and its cost against the best ask: on a book of 50 at 100, 100 at 101 and 200 at 103, a buy of 120 takes all 50 at 100 and 70 at 101, costing 12,070 for a VWAP of 100.583333333 - exactly 70 more than filling entirely at 100 would have cost. Depth is the other honest figure: that book holds 350 in total, so a buy of 1,000 fills only 350 (for 35,700, a VWAP of exactly 102) and leaves 650 unfilled; a pool curve would have quoted the whole size at an ever-worse price, while a book simply runs out. 43. **TWAP oracles (pricing over time, not at an instant).** A spot price can be moved by a single trade in a single slot, so programs that lend or settle against a pool price read a time-weighted average instead: a concentrated-liquidity pool's oracle adds its current tick to a running tick-cumulative counter every second, and the TWAP over a window is `1.0001 ^ ((cumulativeEnd - cumulativeStart) / seconds)`. A window whose cumulative moves from 0 to 360,000 over 3,600 seconds averages tick 100 - a TWAP of 1.010049662 - and against a spot of 1.02 it sits 97.55 bps below spot, because it prices where the pool has been over the whole hour, not where it is now. Two details are the mechanic: the division truncates toward zero (a -100 tick-second change over 3 seconds averages -33, not the floor's -34, and the -1 remainder is discarded), and the window length IS the security parameter - a one-second manipulation moves an hour-long TWAP by roughly one thirty-six-hundredth of its tick distance, while the same long window lags a genuine move just as stubbornly. Shorter windows track faster and protect less; there is no free choice. The hub's calculator (Tool 44) runs the cumulative difference in exact BigInt, reports the truncation remainder, and compares the TWAP with a user-entered spot; the cumulatives are user inputs as an oracle account or explorer reports them, and no live pool or oracle is read.

44. **Burning LP tokens (leaving a pool).** A deposit (item 18) mints LP tokens; leaving is the reverse trade, and it does not hand your deposit back. Burning B of a supply S returns B ÷ S of whatever the pool holds NOW - floor(B × reserve ÷ S) per token, in exact integer math - so every swap, fee accrual and price move since you deposited is inside the numbers you share. Against reserves of 2,000,000 / 500,000 with a supply of 1,000,000, burning 250,000 tokens returns exactly 500,000 and 125,000; if the price had moved since the deposit, the two amounts come back in the pool's CURRENT ratio, which is the realised side of impermanent loss (item 4). Two edges are exact rather than approximate: a full burn returns the whole reserves to the smallest unit and leaves the pool empty, and a dust burn against a large supply can floor to exactly zero on a side - the dust the flooring discards stays in the pool for the remaining LPs, which is also why the last LP out receives fractionally more than a naive share. 45. **Airdrop costs (rent first, fees second).** Sending a token to many wallets costs SOL before any token moves, and the two parts behave differently. A recipient who does not yet hold the mint needs an associated token account created for them (item 27's derivation), and each 165-byte token account locks the rent-exempt deposit of item 2 — 2,039,280 lamports. Locked is not spent: the deposit is reclaimable when the account is closed, but the sending wallet must hold it up front, and at scale it is almost the whole budget. The transfers ride in batched transactions — how many transfers fit in one is the sender's choice, bounded by the 1,232-byte packet limit (item 20) and by whether the creation instructions ride along — and each transaction pays the base fee of item 3 (5,000 lamports for one signature) plus any priority fee. The numbers: 1,000 recipients, 800 of them needing a new account, in batches of 25, at 100 tokens each, take 40 transactions; the rent is 1,631,424,000 lamports (1.631424 SOL), the fees just 200,000 lamports, and the total to fund is 1.631624 SOL plus 100,000 tokens. 46. **Dutch auction decay (the price falls to the first taker).** A Dutch auction inverts the bidding war: the seller publishes a start price, a floor and a duration, and the price falls between them until someone accepts it — in the classic linear form, price(t) = start − (start − floor) × t ÷ duration. A sale from 10 to a floor of 1 over 3,600 seconds stands at 7.75 after 900 seconds and 5.5 halfway, and the ends are exact: the start at t = 0 and the floor the moment the duration runs out, never an asymptote. Many on-chain sales drop the price in steps instead of continuously — a 600-second step leaves that sale at 8.5 at both 900 and 1,199 seconds, stepping to 7 at 1,200 — and a step that does not divide the duration is cut short at the end so the price still finishes on the floor. The buyer's decision is entirely in the schedule: pay now, or wait for a lower price while another buyer can take it first. 47. **Governance quorum and approval (two bars, not one).** A DAO proposal does not pass by winning the argument alone: it must also draw a crowd. Quorum is the participation bar - votes cast (for + against + abstain) must reach a stated share of the governing supply, ceilinged at the smallest unit, so a supply of 10,000,000 at a 10% quorum needs exactly 1,000,000 cast. Approval is the decision bar - for-votes as a share of the decisive votes (for + against), floored to a whole basis point, must reach the threshold. Abstentions are the hinge between them: they count toward quorum, because the holder showed up, and toward neither side of approval. The headline tally makes the trap concrete: 600,000 for, 200,000 against and 100,000 abstaining is a 75% for-share against a 60% threshold - and the proposal still FAILS, because 900,000 cast is 100,000 short of quorum. Raise the for-votes to 700,000 and it passes, cast reaching exactly 1,000,000 with a 77.77% for-share. One-token-one-vote also bounds the tally: votes cast can never exceed the supply, so a larger cast is malformed, not enthusiastic. Real frameworks set their own quorum and threshold and some weigh abstentions or vote weights differently - the hub's calculator (Tool 48) models the convention stated here in exact integer math, and no live proposal is read.

48. **Splitting a fixed supply (allocation buckets and flooring dust).** A launch fixes its total supply at mint time and states the split as shares - liquidity, community, team, treasury - usually in basis points. Pricing each share is floor(supply x bps / 10,000) at the smallest unit, and four floored shares can sum to less than the supply: each floor discards under one smallest unit. Honest splits therefore name ONE remainder bucket that receives supply minus the other floored amounts, so the parts sum to the supply exactly and the dust has a declared home; with four buckets the absorbed dust is provably 0 to 3 smallest units, and at whole-token supplies it is zero - the effect lives only at the smallest-unit scale. The headline split is clean: 1,000,000,000 at 40% liquidity, 25% community and 20% team gives 400,000,000 / 250,000,000 / 200,000,000 and a 150,000,000 treasury remainder (15%). The dust case needs dust-scale inputs: a supply of 1.000000001 at 3,333 bps to each named bucket floors each one to 0.3333, and the treasury's nominal 1 bp floors to 0.0001 - as the remainder it actually receives 0.000100001, one smallest unit of dust richer. Two reading rules for a launch document: the shares must sum to at most 10,000 bps (more promises tokens that do not exist), and the remainder bucket's real share is always at least its stated one. The hub's planner (Tool 49) works the split in exact integer math and reports the nominal share and the dust separately; vesting terms that lock a bucket (item 18) are a separate mechanic and are not applied here.

49. **Quadratic voting (voice priced as the square of votes).** One-token-one-vote (item 47) counts heads; quadratic voting prices conviction: casting v votes on a proposal costs v² voice credits from a fixed budget, so the next vote always costs 2v + 1 more than the last one did - the first vote costs 1 credit, the tenth costs 19. The consequence is arithmetic, not ideology: on a 100-credit budget the most votes any single proposal can receive is floor(√100) = 10, costing exactly 100, while a ballot of 6 votes on one proposal and 8 on another costs 36 + 64 = 100 and speaks with 14 votes in total - breadth beats intensity per credit, which is the design goal for grant rounds and preference aggregation. A ballot whose squares pass the budget is simply uncastable, and the honest figure is by how much. The hub's calculator (Tool 50) prices a three-proposal ballot in exact integer math, reports the marginal cost of the next vote on each proposal, and states the convention it models; frameworks differ in budget, proposal count and whether credits carry over, and no live ballot is read.

50. **Token burns (a bigger share of a smaller supply).** Burning destroys tokens: the supply falls by the burned amount, and a holder who does not burn gains no tokens - they own a larger share of what remains, because the numerator (their balance) stands still while the denominator (the supply) shrinks. Burning 100,000,000 of a 1,000,000,000 supply leaves 900,000,000, and a 10,000,000 balance rises from exactly 1% to 1.11% of the supply (100 to 111 whole basis points, floored). The bound is arithmetic too: a burn of other holders' tokens cannot exceed the supply minus the holder's own balance, and burning all of that leaves the holder at exactly 100%. Two reading rules follow: a burn announcement's honest figure is the share change, not a price promise - destroying supply does not by itself set or raise a price - and floored whole-basis-point shares can hide a dust holder's rise entirely (0 bps before and after) even though the rational share did grow. 51. **Merkle proofs (a root on-chain, a proof per claim).** An airdrop or allowlist with N recipients is commonly committed as a Merkle tree: every recipient is a leaf, pairs hash upward to one root, and only that 32-byte root is stored on-chain. A claim supplies a proof - one sibling hash per level - and the program hashes the leaf up the proof and checks it lands on the stored root, verifying one recipient without storing or revealing the rest. The tree completes to the next power of two at or above N, so depth is the smallest d with 2^d >= N: 10,000 recipients give depth 14, a tree padded to 16,384 leaves with 32,767 nodes, and a proof of 14 hashes - 448 bytes - per claim. The sizes move in steps: 16,384 recipients still fit depth 14 exactly, and recipient 16,385 pushes the whole tree to depth 15 and every proof to 480 bytes; a single recipient is the degenerate case, its leaf being the root and its proof empty. That is the opposite storage choice from a compressed-NFT tree (item 28), which keeps its tree on-chain - a Merkle-committed airdrop keeps only the root there, and the tree itself lives with the distributor. The hub's planner (Tool 52) counts the tree and proof in exact integer math; leaf contents and hash-function choice are stated as not modelled, and no live tree is read.

52. **Multisig thresholds (equal votes, two coalitions to count).** A multisig wallet - Squads is the common Solana form - holds funds under N members and acts only when M of them approve, every member's vote equal, unlike the token-weighted vote of item 47. Two counts describe any M-of-N setup. The approving side: of the 2^N member subsets, those with at least M members can act - a 3-of-5, a 60% threshold, has 16 of the 32 (10 sets of three, 5 of four, 1 of five). The blocking side: the smallest coalition that can stop everything is N − M + 1 refusers, because that many refusals leave fewer than M members able to approve, while one fewer refuser never blocks - so any 3 refusers freeze a 3-of-5, a unanimous 5-of-5 hands every single member a veto (blocking size 1), and a 1-of-3 can only be blocked by all three refusing. Raising M therefore trades liveness for safety in exact steps: each step up shrinks the approving subsets and the blocking coalition together. The hub's planner (Tool 53) counts both in exact integer math and reports approvals still needed against those already collected; member identities, key custody and proposal expiry are stated as not modelled, and no live multisig is read.

53. **Buybacks and burns (revenue in, supply down).** A protocol that earns fees in a quote token can route that revenue into buying its own token back from a pool and burning what it buys - Raydium's fee-funded buyback is the best-known Solana form. The buy is an ordinary constant-product swap, so its cost is the fee plus the price impact the buy itself causes: spending 100,000 of quote into a 1,000,000 / 500,000 pool at a 25 bps fee buys back 45,351.216185496 tokens at an average price of 2.205012531 against a spot of 2, a 9.07% impact - and doubling the spend would pay a worse average price, not a better one, because the buy walks its own price up. Of the tokens bought, the burn share is destroyed and the remainder, if any, goes to the treasury; the supply falls by the burned amount only. Burning everything bought takes a 100,000,000 supply to 99,954,648.783814504 - the burn is 0.0453% of the supply, 4 whole basis points when floored, which is the honest scale of one buyback against a large supply; the effect compounds only across many buybacks. Two reading rules follow: the average price paid, not the spot price, is what a buyback's size costs, and a burn does not by itself set or raise a price - it changes the supply, and any price claim beyond that is a promise this mechanic does not make. The hub's planner (Tool 54) runs the buy through the hub's own swap model and the burn in exact integer math, so its figures cannot disagree with Tools 2 and 51; where the revenue came from, how often buybacks run and any live program are stated as not modelled, and no live pool is read.

54. **Escrow (the fee exists only on the release path).** An escrow trade locks the buyer's payment in a program-controlled account until the seller delivers, so neither side trusts the other with the money first. While the funds sit locked nothing is divided. On release the platform takes its fee and the seller receives the rest: escrowing 10,000 at a 150 bps fee pays a fee of 150 and 9,850 to the seller, and fee plus seller is the escrowed amount exactly, because the fee is the amount times the fee share floored at the smallest unit - which also means a dust payment can floor the fee to zero rather than rounding it up, and the effective share, floored to whole basis points, never exceeds the stated fee. On refund the buyer receives the whole amount back and no fee is charged at all: the fee exists only on the release path. The escrow account itself locks a rent-exempt deposit - 2,282,880 lamports for a 200-byte account, item 3's figure - paid by whoever funds the account and reclaimed when it closes, locked rather than spent. That timing is what separates escrow from a sale split (item 23), which divides a completed sale's price at the moment of sale: escrow divides only on completion, and its refund path divides nothing. The hub's planner (Tool 55) runs the split and the rent in exact integer math; delivery, disputes, arbiter decisions and timeouts are stated as not modelled, and no live escrow is read.

55. **DCA splits (many orders, one curve).** A dollar-cost-averaging program - Jupiter's DCA is the common Solana form - splits one intended buy into N equal orders executed over time, each order floor(total ÷ N) with the first total-mod-N orders carrying one extra smallest unit, so the orders sum to the total exactly. Freeze the pool - no price movement between orders, no replenishment - and the honest result is that splitting buys nothing on execution: 10 orders of 10,000 from a 100,000 total into a 1,000,000 / 1,000,000 pool at a 25 bps fee receive 90,702.432370988, against the lump buy's 90,702.432370993 - a difference of 5 smallest units, flooring dust from each order's output and fee rounding in opposite directions, because walking the same constant-product curve in steps lands where one walk lands. What splitting actually buys is exposure to different prices at different times, which no model can promise; its certain cost is one transaction fee per order - 10 orders at 5,000 lamports each is 50,000 lamports (0.00005 SOL) on top of the pool fees, and the split's total pool fee never exceeds the lump fee, trailing it by fewer than N smallest units because each order's fee floors separately. The hub's planner (Tool 56) runs the split and the lump side by side in exact integer math; between-order price movement and program fees beyond the per-order transaction fee are stated as not modelled, and no live pool or DCA program is read.

56. **DLMM bins (a geometric price ladder).** A discrete liquidity market maker - Meteora's DLMM is the common Solana form - replaces the smooth curve with discrete bins, each holding one fixed price: the price at bin id is (1 + binStep / 10000) ^ id, with the bin step in basis points. The ladder is purely geometric: bin 0 is exactly 1, every step up multiplies by the same ratio, and negative ids divide - the price at -id is the exact reciprocal of the price at id. At a 25 bps step, bin 100 prices at 1.283624888, and a position 20 bins either side spans bin 80 at 1.221097953 to bin 120 at 1.349353547 - a range multiplier of 1.10503301 that depends only on the step and the width, never on where the position sits, because the ladder's ratios are identical everywhere. The price doubles every 278 bins at that step, and halves in the same count. Two consequences follow for a liquidity provider: the width fixed is a width in BINS, not in price, so the same 40-bin position covers a wider price span at a larger step; and a smaller step packs bins tighter - finer prices near the market, but more bins for a position to span and for a swap to cross. This is not the CLMM tick ladder of item 10: a tick scales the square root of the price by 1.0001 per tick, while a bin scales the price itself by (1 + step) per bin. The hub's planner (Tool 57) runs the ladder in exact integer math; per-bin liquidity amounts, the token split a position holds and DLMM's variable volatility fee are stated as not modelled, and no live pool is read.

## 4. Scaffold and test

```bash
anchor init my-program
cd my-program
anchor test
```

`anchor test` runs a local validator and TypeScript tests against your program — the same assertions style this hub uses for its own models.

## 5. Deploy to devnet, honestly

```bash
anchor deploy --provider.cluster devnet
```

Only deploy once tests pass, and label everything you show users for what it is: devnet, testnet, model or live. This hub's rule — no modelled data presented as live, no tool presented as a quote — is a good rule for your app too.
