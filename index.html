Solana in 30 seconds

Accounts & lamports

Everything on Solana is an account: wallets, tokens, programs and data all live in accounts holding lamports, the smallest unit of SOL (1 SOL = 1,000,000,000 lamports). Balances are whole lamports — a SOL amount never has more than 9 decimal places.

Programs

Smart contracts are called programs. They are stateless code; the state they work on lives in separate accounts they own. The SPL Token program, for example, manages every classic Solana token through token accounts it owns.

Fees & rent

A transaction pays a base fee of 5,000 lamports per signature, plus optional priority fees. Accounts pay rent for the data they store — or hold two years of rent up front (the rent-exempt minimum) and pay none again.

Speed

Proof of History gives the network a shared clock before consensus, so validators can order transactions fast: blocks land roughly every 400 milliseconds and finality follows in seconds. That speed is why Solana hosts busy DEXs, payment rails and consumer apps.

Tools — educational models

Each tool runs entirely in your browser and is labelled for what it is: a model that teaches the mechanic, never a live quote.

1. SOL ⇄ lamports converter

Exact conversion with integer math — no rounding, no floating point. Fill in one side and convert.

2. Constant-product swap model

The x·y=k mechanic behind AMM pools across Solana (Raydium CP-Swap, Orca and others): the fee comes off your input, the rest trades against the reserves, and the price moves against you as size grows.

3. Rent-exempt minimum calculator

What an account must hold to be rent-exempt: (128 + data length) × 3,480 lamports per byte-year × 2 years. Try 0 for a plain wallet account, 82 for a token mint, 165 for a token account.

4. Impermanent-loss calculator

For a 50/50 constant-product position: how far the LP position trails simply holding, when the price moves by the ratio you enter — the cost that pool fees have to beat.

5. Transaction fee estimator — base + priority fee

What a transaction costs before rent: a base fee of 5,000 lamports per signature, plus an optional priority fee — ceil(compute-unit limit × compute-unit price ÷ 1,000,000) lamports, where the price is in micro-lamports per compute unit. The priority fee is charged on the limit you request, not the compute you use, and a transaction's limit is capped at 1,400,000 compute units.

6. SPL token amount converter — UI amount ⇄ raw units

SOL's 9 decimals (Tool 1) are just one mint's choice. Every SPL mint sets its own decimals — USDC uses 6, many mints use 9, some use 0 — and token accounts store raw integer amounts in the mint's smallest unit. Wallets show the UI amount: raw ÷ 10^decimals. Fill in one side, with the mint's decimals.

7. Solana address checker — base58 format

Every Solana address is 32 bytes written in base58, the alphabet that omits 0, O, I and l so addresses can't be misread. Paste an address and check its format locally, before you trust it anywhere: every character must be base58 and the decoded value must be exactly 32 bytes. A pasted address with stray extra characters decodes to the wrong length and fails here. This checks format only — not that the account exists, holds anything, or is the address you meant.

8. Staking rewards estimator — epoch compounding

Staking pays once per epoch — 432,000 slots, about 2 days at the target slot time, so about 182.5 epochs a year. Rewards land in the stake account and compound from the next epoch; validators take their commission as a percentage of the reward, not of your stake. Enter a stake, an annual yield you assume, a validator commission, and a number of epochs. The yield is your assumption — this is not a live network yield.

9. Solana Pay URL builder & inspector — transfer requests

Solana Pay encodes a payment request as one URL: solana:<recipient>?amount=…&spl-token=…&reference=…&label=…&message=…&memo=… — the string inside payment QR codes across the ecosystem. The recipient is the base58 address of a native SOL account: associated token accounts must not be used as the recipient, because for a token payment the wallet derives the recipient's token account from the mint you name in spl-token. The amount is in user units — SOL, not lamports; a token's UI amount, not raw units — 0 is valid, leaving it out means the wallet asks the payer, and an amount finer than the asset's decimals (9 for SOL, the mint's own for a token) is malformed. Label and message are display-only; a memo is written on-chain in an SPL Memo instruction and is public forever, so never put anything private in it. A reference is an extra read-only key the wallet attaches to the transfer, so the payment can be found by it later. Build a URL, or paste one in to inspect it — both run locally, nothing is sent and no wallet opens.

10. CLMM tick ⇄ price converter & range checker — concentrated liquidity

Concentrated-liquidity pools — Raydium CLMM and Orca Whirlpools — do not let liquidity sit at any price. Prices are discretised onto ticks: price(tick) = 1.0001^tick, so each tick is one basis point of price, and the on-chain tick range is −443,636 to 443,636. A position only earns fees while the current tick is inside its range (tickLower ≤ tickCurrent < tickUpper); outside it, the position holds only one asset and earns nothing. Both endpoints must be aligned to the pool's tick spacing — set per pool and fee tier, so it is an input here, not a constant. Prices below are in raw token units: a UI price also depends on the two mints' decimals, which this local model does not look up. Convert a tick or a price, then check a range — both run locally. An educational model, not a live pool quote.

11. Slippage tolerance & minimum-received calculator

Every DEX interface on Solana — Jupiter, Raydium, Orca — asks for a slippage tolerance before it sends your swap. The tolerance is the most the price may move against you between the quote and the transaction landing: the wallet computes a minimum received (expected out × (1 − tolerance)) for an exact-in swap, or a maximum input (expected in × (1 + tolerance)) for an exact-out swap, and the on-chain program aborts the swap instead of filling past that bound. Both bounds are rounded against you on purpose — minimum received floors, maximum input floors — so the bound you sign is never looser than the tolerance you picked: an expected 4 at 0.5% protects at 3.98, never rounded back up to 4. Too tight a tolerance and ordinary price movement (or another trade landing first) fails your swap and costs the fee anyway; too loose and a worse fill — including a sandwich attack — still passes. Enter an expected output, an expected input, and a tolerance in basis points (25 bps = 0.25%, 50 bps = 0.5%, 100 bps = 1%). An educational model of the bound, not a live quote.

12. Epoch schedule converter — slot ⇄ epoch, warmup included

Almost every Solana explainer says an epoch is 432,000 slots — and then code quietly computes epoch = slot ÷ 432,000. That formula is wrong, and it has been wrong since genesis: the chain warms up. Epoch 0 holds 32 slots and each warmup epoch doubles (32, 64, 128, …), so the first normal epoch is epoch 14, starting at slot 524,256 — at that slot the naive division says "epoch 1". Only from there is an epoch a constant 432,000 slots, and the correct formula carries the offset: epoch = 14 + (slot − 524,256) ÷ 432,000. Epoch boundaries are when staking rewards land, stake activates and cools down, and leader schedules rotate, so an epoch computed the naive way mis-times all of them. Convert a slot to its epoch, or an epoch to its slot range — both run locally. This is schedule math in slots only: it deliberately does not convert to dates or times, because the target slot duration has changed repeatedly (400 ms for years, cut in stages during 2026) and skipped slots stretch real time further; for a slot's actual timestamp, use getBlockTime or an explorer. An educational model of the runtime's EpochSchedule, not live chain data.

13. Token-2022 transfer fee calculator — withheld on every transfer

Some Solana tokens are minted under the Token-2022 program with a transfer-fee extension: on every transfer the sender is debited the full amount, the recipient is credited the amount minus a fee, and the fee stays withheld inside the recipient's token account until it is harvested to the mint and withdrawn. The classic SPL Token program has no transfer fees — the same transfer of a classic token delivers in full. The program computes the fee on raw amounts (the mint's smallest units — convert with Tool 6): fee = ceil(amount × basis points ÷ 10,000), capped at the mint's maximum fee, and 0 when the rate or the amount is 0. The ceiling matters: any positive transfer at any positive rate pays at least 1 raw unit, so dust transfers of a fee-bearing token can deliver nothing at all. A mint stores an older and a newer fee and picks by epoch; this model prices the single configuration you enter. Work a transfer's fee, or gross up — how much to send so the recipient receives an exact amount. An educational model of the program's fee math, not a live quote.

14. Sandwich attack (MEV) model — what a loose tolerance lets through

A sandwich attack is the canonical MEV extraction on an AMM: an attacker who can see a pending swap buys the same direction first (the front-run pushes the pool price against the victim), lets the victim fill at the worse price, then sells everything back into the price the victim's own trade moved (the back-run). This model runs all three legs through the hub's own constant-product swap (Tool 2) against the reserves each leg leaves behind. The victim's defence is the slippage bound (Tool 11): if the sandwiched fill falls below the minimum received at the victim's tolerance, the victim's transaction aborts — the sandwich makes nothing and the attacker loses the round-trip costs unwinding alone. At a loose tolerance the fill passes its own protection and the attacker's profit comes straight out of the victim's worse price; it is extracted, not created. Defences in the real ecosystem include tight tolerances and private transaction routing that keeps a swap out of the public flow. An educational model of a sandwich on a single pool, not live MEV data.

15. Liquid staking (LST) exchange rate — why the rate rises, not your balance

A liquid staking pool (the SPL Stake Pool program, Marinade, Jito and their peers) holds staked SOL and issues a pool token. That token does not rebase: when staking rewards land, your token balance stays exactly the same — instead the pool's total SOL grows with no new tokens minted, so the exchange rate (total staked SOL ÷ token supply, in SOL per token) rises. Depositing mints deposit × supply ÷ total tokens and redeeming returns redeem × total ÷ supply SOL, both floored like an on-chain division — a dust deposit can floor to zero tokens. This model adds a rewards amount you supply to the total so you can watch the same deposit mint fewer tokens afterwards and the same redemption return more SOL: that difference is the yield. It charges no deposit, withdrawal or epoch fees (real pools charge some — check the pool's own terms) and models no unstake delay: a withdrawal not covered by pool liquidity deactivates stake and waits out the epoch cooldown. An educational model of one pool's exchange rate, not a live pool's rate. Not financial advice.

16. Program-derived address (PDA) finder — seeds, bump and the curve check

Programs own accounts and "sign" without any private key through program-derived addresses: SHA-256(seeds ‖ bump ‖ program ID ‖ "ProgramDerivedAddress"), kept only when the 32-byte hash is not a valid ed25519 point — an on-curve result could have a private key, so it can never be a PDA. Derivation starts at bump 255 and steps down until a hash lands off the curve; about half of all hashes qualify, so the scan usually succeeds within a couple of tries, and the working bump is stored and presented again whenever the program signs with invoke_signed. The runtime's rules: at most 16 seeds, each at most 32 bytes — and seeds are raw bytes: a text seed means its UTF-8 encoding, while many real seeds are a pubkey's 32 bytes (every associated token account is a PDA of the ATA program derived from wallet, token program and mint). This finder derives entirely in your browser — its own SHA-256 and curve check, no lookup, no execution — so the same inputs give this address on every cluster. Try the defaults: the seed vault under the SPL Token program, whose bump-255 candidate lands on the curve and is skipped for bump 254. An educational model of the derivation, not a lookup of any live account. Not financial advice.

17. CLMM position amounts — what a liquidity amount holds

A concentrated-liquidity position on Raydium CLMM or Orca Whirlpools is not opened by handing over a chosen amount of each token. You pick a liquidity amount L and a tick range (Tool 10), and the token amounts follow from the square-root prices: inside the range the position holds L × (1/√Pcurrent − 1/√Pupper) of token0 and L × (√Pcurrent − √Plower) of token1; at or below the lower tick it holds only token0, at or above the upper tick only token1 — the composition slides continuously from one asset to the other as the price crosses the range, which is exactly the position's price exposure. Headline: L = 1,000,000 over ticks −600 to 600 at tick 0 holds about 29,553 of each token. The model uses the shared CLMM formula and was cross-verified against a reference SDK's integer implementation. Amounts are the position's principal in raw token units at the current tick — fees a position earns accrue separately and are not included, and a UI amount also needs each mint's decimals (Tool 6). An educational model, not a live pool quote. Not financial advice.

18. LP deposit & pool share — what a deposit mints

Adding liquidity to a constant-product pool (Tool 2) on Raydium CP, Orca or any x·y=k AMM mints LP tokens in proportion to the smaller side's contribution: minted = supply × min(depositA ÷ reserveA, depositB ÷ reserveB), floored in exact integer math. Only the part of the deposit that matches the pool's ratio is used — the excess of the other token buys no extra LP tokens, so a good interface sizes the deposit to the ratio or returns the excess. The first deposit into an empty pool is different: it sets the starting price and mints the geometric mean, sqrt(depositA × depositB). Headline: against reserves of 1,000,000 A / 4,000,000 B with 2,000,000 LP tokens outstanding, depositing 10,000 A / 50,000 B mints 20,000 LP tokens (0.990099% of the pool): token A limits the mint, only 40,000 of the B is used, and 10,000 B is excess. Amounts are in the tokens' own units — convert with each mint's decimals (Tool 6). An educational model, not a live pool quote. Not financial advice.

19. Token vesting calculator - cliff & linear unlock

Team, investor and ecosystem allocations on Solana commonly vest on a cliff + linear schedule (the shape Jupiter Lock, Streamflow and most launch allocations use): the allocation accrues linearly over the full duration from day one - accrued = total x elapsed / duration, floored at the token's smallest unit - but nothing is claimable before the cliff, and at the cliff the whole accrued share releases at once. Headline: a 1,000,000-token allocation with a 12-month cliff over 48 months has accrued 375,000 tokens (37.5%) by month 18, all of it claimable - but at month 6 it had accrued 125,000 with exactly 0 claimable, and the cliff itself released 250,000 at month 12. This model works in whole months; real schedules run on timestamps, and a minority start the linear accrual at the cliff instead - check which convention your schedule's terms use. An educational model, not a live vesting contract. Not financial advice.

20. Lending health & liquidation calculator

Solana lending markets (Kamino, Marginfi, Drift and peers) judge a borrow position by its health factor: health = (collateral value x liquidation threshold) / debt, where the collateral value is amount x price and the loan-to-value is debt / value. Below a health factor of 1 a market may liquidate - the price where health equals exactly 1 is the liquidation price, debt / (amount x threshold). Borrowing power is set by the lower max LTV, not the threshold: the gap between the two percentages is the market's safety buffer. Headline: 10 tokens at a price of 100 against 500 of debt at an 80% liquidation threshold and a 75% max LTV is worth 1,000 - an LTV of 50%, a health factor of 1.6, a max borrow total of 750 (250 still available), and a liquidation price of 62.5, a fall of about 37.5%. Single collateral and single debt, no interest accrual and no liquidation bonus or fee modelled - real markets weight several assets and accrue interest continuously, so a real health factor drifts even at a flat price. An educational model, not a live lending quote. Not financial advice.

21. Transaction size & packet-limit calculator

Every Solana transaction must fit a single network packet: 1,232 bytes - and its serialized size is exact wire math, not an estimate. Signatures cost a shortvec count plus 64 bytes each, the message header 3 bytes, each static account key a shortvec count plus 32 bytes, the recent blockhash 32 bytes, and one instruction a count byte, a 1-byte program index, a shortvec count plus 1 byte per referenced account, and a shortvec length plus its data. A shortvec length costs 1 byte below 128, 2 below 16,384. Headline: a plain SOL transfer - 1 signature, 3 static keys, 2 instruction accounts, 12 data bytes - is exactly 215 bytes. In a v0 transaction, accounts loaded through an address lookup table cost a 1-byte index each instead of 32 bytes - but the table reference itself costs 32 bytes plus two shortvec counts, so loading a single account through a table makes the transaction 4 bytes bigger; tables pay off from a handful of accounts up (the same transfer with its two non-payer keys in one table is 188 bytes, saving 27). One instruction modelled - each extra instruction adds its own program-index byte, two shortvec counts, account indices and data - and exactly one lookup table; durable-nonce transactions are not modelled. An educational model of the wire format, not a live transaction. Not financial advice.

22. Anchor account space planner

Every account an Anchor program creates starts with an 8-byte discriminator, then its fields serialized by Borsh at fixed sizes — no padding, no alignment: bool and u8 take 1 byte, u16 takes 2, u32 takes 4, u64 takes 8, u128 takes 16 and a Pubkey takes 32. Variable types are sized by the maximum the program declares: a String or a byte vector costs a 4-byte length prefix plus its capacity, a Vec costs 4 plus count × element size, an array costs count × element size, and an Option costs 1 tag byte plus its inner type. Headline: a vault struct of Pubkey + u64 + bool + a 32-character String is 8 + 32 + 8 + 1 + 36 = 85 bytes, locking 1,482,480 lamports as its rent-exempt deposit — space is the deposit, so over-allocating wastes SOL permanently and under-allocating fails the first write that outgrows it. Four fields modelled (structs with more add linearly); enums are not modelled — add 1 byte plus the largest variant per enum by hand. An educational model of the serialization format, not a live account. Not financial advice.

23. Sale split calculator — platform fee, creator royalty, seller remainder

Every marketplace sale and escrow release on Solana splits one price three ways: the platform takes a fee in basis points, the creator takes a royalty in basis points, and the seller receives what is left. The two cuts floor at the smallest unit, like on-chain integer math, and the seller is the remainder — price minus the two floored cuts, never a third independently rounded percentage — so the three parts always sum to the price exactly and no unit is created or destroyed by rounding. The seller keeps the flooring dust too: a 3-unit price split 50/50 pays 1 unit to each cut and 1 unit to the seller. Headline: a sale at 100 with a 200 bps platform fee and a 500 bps royalty pays 2 to the platform, 5 to the creator and 93 to the seller. Both cuts come out of the price in this model — a venue that charges the buyer a fee on top splits differently — and creator royalties on classic Solana NFTs are a marketplace convention (programmable NFTs can enforce them on-chain). An educational model of a sale split, not a live marketplace quote. Not financial advice.

24. Stake activation & cooldown timer — the 9% warmup/cooldown queue

Delegated stake never switches on or off at once. At each epoch boundary the stake program lets only a rate-limited share of the cluster change state: an account's allowed change is its portion ÷ the total moving the same way × the cluster's previous-epoch effective stake × the warmup/cooldown rate, floored, never more than its own remaining portion, and always at least 1 lamport while a portion remains. The rate is 900 bps (9%) on the current network — it was 2,500 bps (25%) before the reduce_stake_warmup_cooldown feature — so at most 9% of the cluster's effective stake may activate or deactivate per epoch, shared pro-rata by everything moving that epoch. That is why a normal stake (far below 9% of the cluster) is fully effective after one epoch, while a whale-sized movement, or a crowd all heading for the exit together, queues over several. Headline: 40,000,000 SOL activating solo against a 400,000,000 SOL cluster moves 36,000,000 in epoch 1 and the last 4,000,000 in epoch 2. This model holds the cluster's effective stake constant at your figure (on-chain it is last epoch's stake-history entry and drifts) and assumes other movers drain at the same fractional pace. An educational model of stake warmup and cooldown, not a live staking quote. Not financial advice.

25. CLMM uncollected fees calculator — fee growth since the last touch

A concentrated-liquidity position (Raydium CLMM, Orca Whirlpools) never stores a running "fees earned" total. The pool keeps fee-growth counters: fees accrued per unit of liquidity, in X64 fixed point (scaled by 264) and stored as u128 integers — a global counter per token, an "outside" counter per tick, and in each position the fee growth inside its range at its last touch. The growth inside is global − below the lower tick − above the upper tick (the SDK computes it for you), and what the position has earned since that touch is floor((inside now − inside last) × liquidity ÷ 264), plus whatever an earlier touch already settled into its tokens-owed balance. The subtraction wraps modulo 2128, exactly like the on-chain u128 arithmetic: a counter that has passed its stored value on the way around is not an error, and its delta is still the true small increment. That is also why the counters are integers far beyond float range — this calculator takes them as whole integers and does exact BigInt math, never a float. Headline: liquidity 1,000,000 with token A's growth up exactly 264 (1.0 per unit of liquidity) accrues exactly 1,000,000 raw units. The growth counters are inputs here, as an explorer or the SDK reports them — this tool reads no live position. An educational model of CLMM fee accounting, not a live position quote. Not financial advice.

26. Inflation schedule calculator — how fast new SOL is issued

SOL has no supply cap: new SOL is issued every epoch as staking rewards, at a rate set by the network's inflation schedule — three parameters in the validator code: an initial rate of 8% per year, a disinflation rate of 15% per year, and a long-term terminal rate of 1.5% the schedule never falls below: rate = max(1.5%, 8% × (1 − disinflation)years). The year is fractional on-chain — the validator recomputes the rate every epoch from the fraction of a year elapsed since inflation began at epoch 150 (February 2021), so the rate glides down continuously rather than stepping once a year. Headline: at year 5 the rate is 3.5496%, which on a supply of 500,000,000 SOL issues 17,748,212.5 new SOL that year; the terminal floor arrives at year ≈10.30 (the first whole year at 1.5% is year 11). The disinflation rate is an input so the governance change adopted in 2026 — doubling it to 30%, which would pull the floor forward to year ≈4.69 — can be modelled honestly: it is not yet implemented in the validator, so 1,500 bps (15%) remains the shipped schedule. Annual issuance here holds the supply at the figure you enter; on-chain the supply itself grows by the issuance. An educational model of the inflation schedule, not live network data. Not financial advice.

27. Associated token account finder — the one canonical token account per wallet and mint

Almost every token balance on Solana lives in an associated token account: one canonical token account per (owner, mint) pair, whose address is not a keypair but a program-derived address under the Associated Token Account program (ATokenGPvbdGVxr1b2hvZbsiqW5xWH25efTNsLJA8knL), derived from the seeds [owner, token program, mint] in exactly that order. That is why a wallet never has to remember token account addresses — any app can recompute them from the wallet and mint alone. The token program seed is why the same wallet and mint have different ATAs for the classic SPL Token program and for Token-2022. Headline: this hub’s donation address G7xepVyQSrxtH61ZooXvPAmnS8omQ1TvHqB8qDmHXWm holding the USDC mint EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v under the classic token program has the ATA BeJv9nhxhAhGVUpVaN4USa9TgpGiYhauc6VU5QyQZrbq (bump 255). The owner may itself be a PDA — the derivation never requires the owner to be on the ed25519 curve. Not financial advice.

28. Compressed NFT tree planner — what a concurrent Merkle tree account costs

A compressed NFT has no token account of its own: the asset lives off-chain in an indexer, and the only on-chain state is one concurrent Merkle tree account (SPL account compression — the structure Metaplex Bubblegum mints into). Creating that account is a one-time rent decision made from three numbers chosen up front. The account is a 56-byte header, 64 bytes of counters and rightmost-path fixed data, a changelog ring of bufferSize × (40 + 32 × maxDepth) bytes — one entry per recent change, each holding a root, an index and one hash per tree level, which is what lets many mints update the tree concurrently — plus 32 × maxDepth bytes of rightmost proof, plus an optional canopy that stores the top levels on-chain so later transfers supply fewer proof hashes. The changelog is almost the whole account: the headline tree below (depth 14, buffer 64, no canopy) is a 31,800-byte account locking 222,218,880 lamports (0.22221888 SOL) of rent for a capacity of 16,384 assets — and 31,232 of its bytes are the changelog ring. The buffer size must be a power of two (the ring is indexed by mask), a tree holds 2^maxDepth assets, and past depth 17 Bubblegum's tree creation requires a canopy of at least maxDepth − 17. Creation also pays a normal transaction fee and minting into the tree is a separate cost — neither is modelled. An educational model of the tree account layout, not a live quote. Not financial advice.

29. Seeded address finder — createWithSeed (base + seed + owner)

Solana's other deterministic address, older than the PDA: the system program's create_account_with_seed derives an account address as SHA-256(base ‖ seed ‖ owner) — the base signer's 32 bytes, one seed string, and the 32 bytes of the program that will own the account. That is the whole formula: no marker string, no bump byte, and no ed25519 curve check — a seeded address may land on the curve and is still valid, because nobody needs (or could know) a private key for it; the base signed its creation. This is how the CLI fans one keypair out into many stake accounts — solana create-address-with-seed --from <base> 0 STAKE, then seed 1, 2, … under the Stake program. The seed is at most 32 bytes as UTF-8 and is used exactly as typed (spaces are bytes — it is never trimmed). Headline: this hub's donation address as base, seed 0, the Stake program (Stake11111111111111111111111111111111111111) as owner derives 4z22cSCVREYe519iEet4xdqBSrTDx9muhtRR3fcRxpod — an on-curve result that a PDA search would have rejected. An educational model of seeded-address derivation, not a live account lookup. Not financial advice.

30. Token valuation calculator — market cap & fully diluted valuation (FDV)

Every token page quotes two valuations from the same price: market cap = price × circulating supply — the supply actually trading today — and the fully diluted valuation (FDV) = price × max supply — what the token would value at if every token that will ever exist already did, at today's price. Between them sits the total minted supply: minted but not circulating (locked, treasury, still vesting — Tool 19) is the unlock overhang, and max minus total is not yet minted at all. The FDV ÷ market cap multiple is a pure supply ratio (max ÷ circulating — the price cancels), so it measures dilution still to come, not price. Headline: at a price of 2.5, a circulating supply of 400,000,000 against a total of 800,000,000 and a max of 1,000,000,000 gives a market cap of 1,000,000,000 and an FDV of 2,500,000,000 — 2.5× the market cap, with only 40% of the max supply circulating. All products floor in exact integer math, and the two gap values are differences of the floored valuations so the parts sum exactly to the FDV. The price and supplies are your inputs — no live price or mint is read. An educational model of token valuation, not live market data. Not financial advice.

31. Address lookup table planner — table account size, rent & per-transaction savings

A v0 transaction can load accounts through an address lookup table: an on-chain account holding up to 256 addresses (the indexes are u8, one byte each) that transactions reference by index instead of writing out each 32-byte key. The account's layout is fixed: 56 bytes of metadata (deactivation slot, last-extended slot, authority) + 32 bytes per stored address, priced with the rent formula of Tool 3 — a full table is 8,248 bytes locking 58,296,960 lamports, and the headline table below storing 64 addresses is a 2,104-byte account locking 15,534,720 lamports (0.01553472 SOL). In a transaction the lookup section costs 1 byte for the table list, the table's own 32-byte key, two shortvec counts and 1 byte per loaded address — exactly Tool 21's lookup figure — so loading one address this way costs 4 bytes more than inlining it, while the headline load of 20 addresses (12 writable, 8 readonly) costs 55 bytes instead of 640, saving 585 bytes in every transaction that loads them. The deposit is reclaimable only by deactivating the table and waiting out the cooldown until its deactivation slot leaves the SlotHashes sysvar — stated here, not modelled; one table per transaction is modelled. An educational model of the lookup-table layout, not a live account lookup. Not financial advice.

32. Oracle price confidence interpreter — what a Pyth-style price ± conf really says

An oracle feed on Solana (Pyth is the one most lending markets and DEXs consume) does not publish a single price: it publishes price, conf and expo — the price is price × 10expo, and conf, at the same exponent, is a confidence interval of roughly one standard deviation: the publishers' aggregate estimate is that the true price sits within price ± conf about 68% of the time. The headline feed below — 150.00 ± 0.075 — has a band only 5 bps wide, while the textbook example of 67,890 ± 680 is 100.16 bps wide and would fail a strict 1% (100 bps) guard by a hair: programs defend themselves exactly this way, rejecting a price whose conf exceeds a chosen share of the price and valuing collateral at the band's low end rather than the mid price. Staleness (checking the publish time against a maximum age) is the feed's other safety check and is stated here as not modelled. An educational model of oracle price confidence, not a live feed reading. Not financial advice.

33. Bonding curve model — how a launchpad prices a token before any pool exists

34. Perpetual funding payment model — what holding a perp costs (or earns) per hour

35. Lending interest-rate model — the kinked curve that prices a borrow

Solana lending markets (Kamino, Marginfi, Drift, Save and others) do not set borrow rates by hand: they read them off a kinked curve of utilization — borrowed ÷ supplied. 36. Perpetual position margin, PnL & liquidation price

A perpetual position is judged on its margin, not its size: at leverage L you post initial margin = notional ÷ leverage, your unrealised PnL is (mark − entry) × size for a long (mirrored for a short), and your equity is margin + PnL. The venue liquidates when equity falls to the maintenance margin — a rate (an input here: every venue sets its own, often tiered by size) times the current notional — which is why liquidation strikes while money still remains: the headline long of 100 units at 150, 10x leverage, a 500 bps maintenance rate posts 1,500 of margin and is liquidated at 142.105263157, a fall of only about 5.26%, even though its margin would not reach zero until 135. A long at leverage 1 or below has no liquidation price at all — its margin covers the whole notional, so no fall can reach the line. 37. Stableswap swap model — the invariant that prices stable pools near 1:1

Pools of like-valued tokens (a USDC/USDT pair) do not use the constant-product curve of Tool 2 — that curve prices every pool as if its tokens could diverge, and charges for it. A stableswap pool (the Curve-style invariant behind Saber and other stable pools on Solana) blends a constant-sum line with constant-product: its invariant D is solved from the balances and an amplification coefficient A — as A grows the price holds near 1:1 while the pool stays balanced, and as the pool unbalances (or A falls) the curve bends back toward constant-product pricing. The headline pool of 1,000,000 / 1,000,000 at A = 100 has D = 2,000,000 and returns a 10,000 trade at 9,999.502463058 gross — a price impact of under 0.005%, against 9,900 on the constant-product curve — before its 4 bps fee, charged on the output, leaves 9,995.502662073. Unbalance the same pool to 1,500,000 / 500,000 and the trade returns 9,910.453997586 gross: the curve defends the peg only while liquidity backs it. D and the post-trade balance have no closed form, so both are solved by integer Newton iteration in exact BigInt — the method the on-chain programs themselves use, which can sit a few smallest units from the real-valued curve on extreme inputs. 43. Limit-order book walk - what a market buy actually pays

Every other swap tool on this hub prices against a pool curve. A central limit order book (Phoenix, OpenBook and Manifest on Solana) works the other way: traders rest limit orders at their own prices, and a market buy walks the ask side - it fills at the best (lowest) ask first, then the next, at each resting order's own price, until the buy is filled or the book runs out. 44. TWAP oracle calculator - the time-weighted average price

A lending market or a cautious swap program rarely trusts a pool's spot price - one trade can move it. What it reads instead is the pool's TWAP oracle: the pool adds its current tick to a running tick cumulative counter every second, and the time-weighted average price over any window is 1.0001^(cumulative change ÷ seconds). The headline window - a cumulative that moves from 0 to 360,000 over 3,600 seconds - averages tick 100, a TWAP of 1.010049662, sitting 97.55 bps below a spot price of 1.02: that gap is the lag, the price the pool has been at rather than the price it is at now. The division truncates toward zero, as the on-chain integer math does - a falling market averaging -33 ticks from a -100 change over 3 seconds, not -34 - and the discarded remainder is reported, not hidden. A longer window smooths a spike further and lags a real move longer; that trade-off is the whole design. The cumulatives and the spot are your inputs, as a pool's oracle account or an explorer reports them. An educational model of a TWAP oracle, not a live quote. Not financial advice.

48. Governance quorum & approval calculator — did the DAO vote actually pass?

49. Token supply allocation planner — splitting a fixed supply into buckets

50. Quadratic voting cost calculator — voice priced as the square of votes

52. Merkle airdrop proof planner — one root on-chain, a proof per claim

An airdrop or allowlist does not store every recipient on-chain: each recipient is a leaf in a Merkle tree, pairs of hashes combine upward to a single root, and only that 32-byte root goes on-chain. A claim then supplies a proof — one sibling hash for each level of the tree — and the program hashes the claim up the proof and checks that it lands on the stored root. The tree is completed to the next power of two: 10,000 recipients need a tree of depth 14 padded to 16,384 leaves (32,767 nodes in total), and every claim carries a proof of 14 hashes, 448 bytes. Proof size moves in steps, not smoothly: 16,384 recipients still fit depth 14 exactly, while recipient 16,385 pushes the whole tree to depth 15 and every proof to 480 bytes. A single recipient is the degenerate case — the leaf is the root and the proof is empty. This model counts the tree and the proof; the leaf contents, the hash function and any claim program are not modelled, and a compressed-NFT tree (Tool 28), which stores its tree on-chain, is a different structure. An educational model of a Merkle proof, not a live airdrop. Not financial advice.

53. Multisig approval planner — how many keys must agree, and how few can block

A multisig wallet (Squads is the common Solana form) holds funds under N members and acts only when M of them approve — every member's vote equal, unlike a token-weighted DAO vote (Tool 48). Three counts describe the setup. A 3-of-5 threshold is 60% of the members, and 16 of the 32 possible member subsets are large enough to approve (10 sets of three, 5 of four, 1 of five). The mirror count is the smallest blocking coalition: N − M + 1 members refusing makes approval unreachable, so a 3-of-5 is blocked by any 3 refusers, a unanimous 5-of-5 hands every single member a veto, and a 1-of-3 can only be blocked if all 3 refuse. Raising M buys safety against stolen keys and sells liveness — more approvals to collect before anything can move. This model counts subsets and coalitions in exact integer math; member identities, key custody, proposal expiry and any live multisig are not modelled. An educational model of a multisig threshold, not a live wallet. Not financial advice.

56. DCA execution planner — what splitting one buy into many orders does, and does not, do

57. DLMM bin price planner — the ladder a discrete-bin pool prices on

A classic (non-compressed) Metaplex NFT is not one thing on-chain: it is four accounts, each funded rent-exempt when the mint is created — the mint itself (82 bytes, 1,461,600 lamports), the holder's token account (165 bytes, 2,039,280), the metadata account (allocated at its 679-byte maximum, 5,616,720) and, when one is created, the master edition account (282 bytes, 2,853,600). Every figure is Tool 3's rent run verbatim on those sizes, so the tools cannot disagree. The full recipe is 11,971,200 lamports (0.0119712 SOL) per NFT — the origin of the rule of thumb that a Solana NFT costs about 0.012 SOL before fees — and minting 100 of them locks 1,197,120,000 lamports (1.19712 SOL) across 120,800 bytes of accounts. The deposits are locked, not spent: closing an account reclaims its deposit, but the minter must hold the full amount up front, which is why large drops stage their funding. This is the classic structure; a compressed NFT (Tool 28) stores its state in one shared tree account instead and is a different cost entirely. An educational model of a classic NFT mint's rent, not a live quote. Not financial advice.

59. Program deploy cost planner — what a .so file locks up

Deploying a program through the upgradeable loader is not one account either: it creates a program account (36 bytes, 1,141,440 lamports) and a programdata account — a 45-byte header plus the space allocated for the program's bytes at the deploy's maximum data length — each funded rent-exempt. Before either exists, the upload stages the bytes in a buffer account (a 37-byte header — the same layout minus the slot field — plus the same maximum length) whose deposit is reclaimed when the deploy completes: it counts toward the peak the deployer must hold, not the amount left locked, and the 8-byte header gap makes it exactly 55,680 lamports smaller than the programdata deposit. A 200,000-byte program deployed at exactly its own size locks 1,394,345,520 lamports (1.39434552 SOL) — programdata 200,045 bytes at 1,393,204,080 — and peaks at 2,787,493,920 lamports (2.78749392 SOL) while the buffer is funded. Every figure is Tool 3's rent run verbatim on those sizes. Allocating a larger maximum leaves headroom for upgrades at exactly 6,960 lamports per reserved byte — the same per-byte figure an extension would charge later, so reserving now and extending later cost the same rent; only the timing differs. The deposits are locked, not spent: closing a program reclaims them. An educational model of a program deploy's rent, not a live quote. Not financial advice.

60. CLMM impermanent-loss calculator — a concentrated position against just holding

Tool 4 prices impermanent loss for a full-range pool; a concentrated position (Raydium CLMM, Orca Whirlpools) loses differently, because it only rebalances inside its tick range. This model runs Tool 17 at two ticks with the same liquidity and range: the amounts held at the entry tick are the just-hold portfolio, the amounts at the exit tick are the position, and both are valued in token1 at the exit price. A position of liquidity 1,000,000 over ticks -600 to 600, entered at tick 0 holding 29,553.010879134 of each token, is worth 60,005.999255043 in token1 terms if the price leaves the top and reaches tick 1,200 (price 1.127490087), while holding the entry amounts is worth 62,873.737688415 — an impermanent loss of 4.561107%, and it keeps widening past the range because the position, now entirely token1, stopped rebalancing at the upper tick while the held token0 kept appreciating. An exit exactly at either range bound loses 1.521965% either way, no price move loses exactly zero, and as the range widens toward the full tick range the figure converges to Tool 4's constant-product loss for the same price move. Swap fees the position earns are not included — they are Tool 25's figures, and they are what offsets this loss in practice. An educational model of a concentrated position against holding, not a live quote. Not financial advice.

61. Options payoff calculator — what a long call or put is worth at expiry

Beside the perpetuals of Tools 34 and 36, Solana derivatives venues (Drift, Zeta) trade options: a long call pays max(expiry price − strike, 0) per unit at expiry, a long put pays max(strike − expiry price, 0), and the buyer paid the premium up front — so the net is payoff minus premium and the most a long option can ever lose is exactly that premium. The headline long call, strike 150, premium 5, over 100 units, at an expiry price of 180 pays 3,000 against a 500 premium — a net of +2,500, +500% on the premium — and breaks even at exactly 155, the strike plus the premium (a put breaks even at strike minus premium: the mirror put at an expiry of 120 nets the same +2,500 and breaks even at 145). At or beyond the wrong side of the strike the payoff is zero and the whole premium is lost; a put's payoff is capped at the strike (an expiry of zero pays 15,000 on the headline terms, a net of 14,500), and a put whose premium exceeds its strike has no break-even at or above zero at all — even a zero expiry pays less than it cost. Only the long side at expiry is modelled: no time value, volatility, early exercise or trading fees, and a short position's profile is the mirror image with margin on top. An educational model of an option's expiry payoff, not a live quote. Not financial advice.

62. Blockhash expiry checker — how long a signed transaction can still land

Every Solana transaction carries a recent blockhash, and the runtime only processes it while that blockhash is recent enough: the maximum processing age is 150 blocks, which is why the RPC's getLatestBlockhash returns a last valid block height — the block height the blockhash came from, plus 150. The count is in block height, not slots: a skipped slot produces no block and does not age a blockhash, so wallets track expiry by height even though the epoch schedule (Tool 12) runs on slots. Because the age is 0-indexed, a blockhash can land at 151 distinct block heights — its own height through its last valid height, inclusive — and one block past that it is expired forever: the transaction must be rebuilt and re-signed on a fresh blockhash. The headline blockhash, from block height 250,000,000, seen at a current height of 250,000,120, is 120 blocks old with a last valid height of 250,000,150 — 30 blocks remaining. A durable-nonce transaction is the exception — its stored nonce value does not age this way — and is not modelled here, and no wall-clock time is quoted: the window is counted in produced blocks, never seconds. An educational model of blockhash expiry, not a live cluster reading. Not financial advice.

63. Anchor discriminator finder — the 8 bytes that name an instruction or account

An Anchor program never dispatches on a name string: every instruction call's data begins with an 8-byte discriminator — the first 8 bytes of the SHA-256 hash of global:<name>, where the name is the Rust function name in snake_case, exactly as declared — and every Anchor account's data begins with the same construction over account:<name>, the Rust struct name in PascalCase (Tool 22 budgets those 8 bytes at the front of every account). The headline instruction, initialize — the first instruction of nearly every Anchor program — hashes to afaf6d1f0d989bed, the byte list [175, 175, 109, 31, 13, 152, 155, 237]. The hash is case-sensitive: Initialize is a different discriminator, so renaming or recasing a function or struct silently changes it and breaks every existing client and account — the discriminator is part of a program's public interface, not an internal detail. Only the default hash-derived discriminator is modelled: newer Anchor versions let a program set a custom discriminator override instead, and those programs do not use this hash. An educational model of Anchor's default discriminator, not a live program reading. Not financial advice.

64. Account reallocation planner — growing an account 10,240 bytes at a time

A program can resize its own account with realloc, but the runtime caps each single growth at 10,240 bytes (10 KiB) — growing by more takes that many separate realloc calls — while shrinking in one call is uncapped, and no account may exceed 10 MiB (10,485,760 bytes) of data. The account must stay rent-exempt at its new length, so growth needs a top-up of exactly the rent difference (Tool 3's figures at the two lengths, 6,960 lamports per added byte), and shrinking releases the same figure back. Growing a 1,024-byte account to 100,000 bytes is 98,976 bytes of growth: 10 realloc calls (the last grows the remaining 6,816 bytes) and a top-up of 688,872,960 lamports (0.68887296 SOL). An educational model of account reallocation, not a live account reading. Not financial advice.

65. Durable nonce planner — pre-signing transactions that do not expire in 150 blocks

A normal transaction dies 150 blocks after its blockhash (Tool 62). A durable nonce transaction signs against the blockhash stored in a nonce account instead, and its first instruction must be AdvanceNonceAccount — which replaces the stored value the moment the transaction lands, so each stored value backs exactly one transaction and the transaction carries no block-height expiry until the nonce advances. The account's state is 80 bytes and must be rent-exempt, so each account locks 1,447,680 lamports (Tool 3's figure for 80 bytes) — locked, not spent, and reclaimed when the account is closed. Pre-signing 10 transactions that may land in any order takes 10 nonce accounts, locking 14,476,800 lamports (0.0144768 SOL); an ordered chain can share one account, because each advance produces exactly the value the next transaction signed against, but it must then land strictly in signing order. The nonce authority must sign the advance, and an account's stored value can also be advanced by hand, which invalidates anything signed against the old value. An educational model of durable-nonce planning, not a live account reading. Not financial advice.

Getting started building on Solana

  1. Install the Solana CLI from the official installation guide, then point it at devnet: solana config set --url devnet.
  2. Make a devnet wallet and fund it free: solana-keygen new, then solana airdrop 2. Devnet SOL has no value — it exists so you can break things safely.
  3. Learn the account model first (Tool 3 above): every program you write allocates accounts, and rent-exempt minimums decide how much SOL each one locks up.
  4. Price a transaction before you send it (Tool 5 above): 5,000 lamports per signature plus a priority fee charged on the compute-unit limit you request — simulate, then set the limit close to real usage instead of overpaying for headroom you never use.
  5. Convert token amounts with the mint's own decimals (Tool 6 above): token accounts store raw integers, and the same raw number is a different UI amount under every mint — read the decimals off the mint before you move an amount between code and UI.
  6. Check every address before you trust it (Tool 7 above): an address is 32 bytes in base58 — a paste with stray or missing characters decodes to the wrong length. Format is only the first check; still compare the full address character-for-character with its source.
  7. Model staking before you delegate (Tool 8 above): rewards arrive once per epoch (about 2 days), commission comes off the reward — not the stake — and credited rewards compound. Compare validators on commission and reliability, never on a headline yield alone; the yield you model is an assumption, not a promise.
  8. Read a payment link before you pay it (Tool 9 above): a Solana Pay URL names the recipient, the amount in user units and the asset — an empty amount means the wallet asks, a memo is public on-chain forever, and a well-formed link can still point at the wrong recipient, so inspect it and compare the recipient in full.
  9. Place concentrated liquidity by ticks, not vibes (Tool 10 above): on Raydium CLMM and Orca Whirlpools a price is a tick — price = 1.0001^tick — a position earns only while the current tick is inside its range, and its endpoints must align to the pool's tick spacing. A narrow range earns more per unit while it lasts and goes inactive sooner; check both before you open one.
  10. Set slippage deliberately on every swap (Tool 11 above): the tolerance becomes a signed bound — minimum received = expected out × (1 − tolerance), floored, or maximum input = expected in × (1 + tolerance) — and the program aborts rather than fill past it. Too tight and normal price movement fails the swap (you still pay the fee); too loose and a bad fill, or a sandwich, passes. Basis points are the unit: 50 bps = 0.5%.
  11. Never compute an epoch as slot ÷ 432,000 (Tool 12 above): the chain warmed up — epochs doubled from 32 slots until the first normal epoch, 14, at slot 524,256 — so the naive division is a dozen-plus epochs behind, forever. Epoch boundaries are when staking rewards land and leader schedules rotate; use the runtime's EpochSchedule (or this converter), and never convert slots to wall-clock time with a fixed slot duration — the target has changed repeatedly.
  12. Check whether a token withholds a transfer fee (Tool 13 above): a Token-2022 mint can carry a transfer fee — the sender is debited in full, the recipient is credited the amount minus ceil(amount × rate ÷ 10,000), capped at the mint's maximum fee, and the withheld fee sits in the recipient's token account until harvested. A quote or invoice in such a token that ignores the fee under-delivers on every payment; gross up when an exact received amount matters, and remember the classic SPL Token program has no transfer fees at all.
  13. Understand what a sandwich does to a loose tolerance (Tool 14 above): an attacker front-runs a visible swap, lets it fill worse, and back-runs into the price move — the profit is the victim's loss. The slippage bound is the defence: tight enough and the victim's transaction aborts instead of filling (the attacker then loses the round-trip unwinding alone); loose enough and the bad fill passes its own protection. Private routing keeps a swap out of the public flow the attack reads.
  14. Price a liquid staking token by its rate, not its balance (Tool 15 above): an LST does not rebase — rewards grow the pool's total SOL while the supply stands still, so the SOL-per-token rate rises and the same token amount redeems for more SOL over time. A rate below 1, or a deposit that mints at a stale rate, is a red flag; and a dust deposit can floor to zero tokens, so never deposit an amount whose minted figure you have not checked.
  15. Derive program addresses from seeds, never store a key for them (Tool 16 above): a PDA is SHA-256(seeds ‖ bump ‖ program ID ‖ "ProgramDerivedAddress") kept only when the hash lands off the ed25519 curve — a result on the curve could have a private key and is rejected, which is why derivation scans bump 255 downward for the first off-curve hash. At most 16 seeds, each at most 32 bytes; seeds are raw bytes (text means its UTF-8 encoding; a pubkey seed is its 32 bytes — an associated token account is exactly this derivation). A PDA has no private key: only its program can sign for it, with those seeds and that bump.
  16. Size a concentrated position from its liquidity, not from token amounts (Tool 17 above): a CLMM position is L plus a tick range, and the amounts follow — inside the range it holds both assets in the proportion the current tick sets, below the range only token0, above it only token1, sliding continuously as the price crosses. At tick 0 over −600…600, L = 1,000,000 holds about 29,553 of each. The amounts are principal only: earned fees accrue separately, and every price move re-splits the position toward the asset being sold — that drift is the exposure behind impermanent loss.
  17. Deposit into a pool at its ratio, not yours (Tool 18 above): a constant-product pool mints LP tokens from the smaller side's contribution — supply × min(depositA ÷ reserveA, depositB ÷ reserveB) — and only the ratio-matching part of a deposit is used, so an off-ratio deposit wastes the excess unless the interface returns it. The first deposit is the exception: into an empty pool it sets the starting price and mints sqrt(depositA × depositB). Your share afterwards is minted ÷ new supply, and burning it later returns that share of whatever the pool holds then — not what you put in.
  18. Read a vesting schedule by its cliff, not its accrual (Tool 19 above): an allocation can accrue linearly from day one yet be claimable for exactly 0 until the cliff month, when the whole accrued share releases at once - a 1,000,000-token allocation on a 12-month cliff over 48 months shows 125,000 accrued and 0 claimable at month 6, then 250,000 released at the cliff. Schedules differ: some start the linear accrual at the cliff instead of gating it, and real contracts run on timestamps, not whole months - read the terms before valuing any locked allocation.
  19. Judge a borrow by its health factor, not its LTV alone (Tool 20 above): a lending position is liquidatable when (collateral value x liquidation threshold) / debt falls below 1 - 10 tokens at 100 against 500 of debt at an 80% threshold has a health factor of 1.6 and a liquidation price of 62.5. The max LTV is the borrowing limit, the threshold is the liquidation line, and the gap between them is the safety buffer; interest accrual moves a real health factor even at a flat price.
  20. Budget a transaction's bytes like its fees (Tool 21 above): a transaction must fit one 1,232-byte packet - a plain SOL transfer is exactly 215 bytes (65 of signatures, 97 of static keys, 32 of blockhash, the rest header and instruction). Lookup tables shrink big transactions because a table account costs a 1-byte index instead of a 32-byte key, but the table reference costs 32-plus bytes first: loading one account through a table makes a transaction bigger, loading many makes it much smaller.
  21. Size every account before you allocate it (Tool 22 above): an Anchor account is 8 discriminator bytes plus its Borsh field bytes, packed with no padding — Pubkey 32, u64 8, bool 1, a String 4 plus its maximum length — and the total is exactly the rent-exempt deposit it locks: a vault struct of Pubkey + u64 + bool + String(32) is 85 bytes and 1,482,480 lamports. Over-allocate and the waste is permanent; under-allocate and the first write that outgrows the space fails.
  22. Time a stake's warmup or cooldown by the queue, not the calendar (Tool 24 above): stake changes state only at epoch boundaries, and per epoch at most 9% of the cluster's effective stake may activate or deactivate in total (900 bps; it was 25% before the rate reduction), shared pro-rata by everything moving — your epoch change is your portion ÷ the total moving × that cap, floored, with a 1-lamport minimum. A stake small against the cluster is fully effective after one epoch; whale-sized moves and crowded exits take several, which is why an unstake can still be draining after the epoch rolls.
  23. Read a CLMM position's fees from its counters, not a balance (Tool 25 above): uncollected fees are floor((fee growth inside now − at last touch) × liquidity ÷ 264) plus what an earlier touch already settled as owed — and the subtraction wraps modulo 2128, so a counter lower than its stored value is the u128 wrapping, not negative fees. Touching a position settles and re-stores the counter, which is why "since the last touch" is the only span the growth delta ever describes.
  24. Price dilution from the schedule, not from headlines (Tool 26 above): new SOL is issued at max(1.5%, 8% × 0.85years) — at year 5 that is 3.5496%, and the 1.5% terminal floor arrives at year ≈10.30, so issuance never stops, it just slows to the floor. The rate glides per epoch (the year is fractional on-chain), and a governance-adopted doubling of the disinflation rate to 30% is not a live parameter until the validator implements it — model it at 3,000 bps, don't quote it as current.
  25. Budget a compressed NFT collection by its tree, not per asset (Tool 28 above): a cNFT collection's on-chain cost is one concurrent Merkle tree account — 56 bytes of header, 64 fixed, a changelog ring of buffer × (40 + 32 × depth) bytes, 32 × depth of rightmost proof, plus any canopy — and the ring is almost all of it: a depth-14, buffer-64 tree is 31,800 bytes and 222,218,880 lamports of rent for 16,384 assets, of which 31,232 bytes are changelog. Depth sets capacity (2depth), the buffer (a power of two) sets how many concurrent updates the tree absorbs, and a canopy trades more rent up front for fewer proof hashes on every later transfer.
  26. Derive a seeded address when a signer — not a program — needs many accounts (Tool 29 above): a seeded address is SHA-256(base ‖ seed ‖ owner) — no marker, no bump, no curve check, so an on-curve result is valid (the hub's donation address with seed 0 under the Stake program derives 4z22cSCVREYe519iEet4xdqBSrTDx9muhtRR3fcRxpod). Reach for a PDA (Tool 16) when a program must sign; reach for a seed when a base keypair creates a family of accounts, one seed per member, and signs their creation itself. The seed is a single string of at most 32 UTF-8 bytes, used byte-for-byte.
  27. Read a token's valuation by which supply it multiplies (Tool 30 above): market cap is price × circulating supply, FDV is price × max supply, and the multiple between them is max ÷ circulating — the price cancels, so it is pure dilution still to come. At a price of 2.5 with 400,000,000 circulating of a 1,000,000,000 max, the market cap is 1,000,000,000 and the FDV 2,500,000,000: only 40% of the supply trades today, and the FDV assumes today's price survives the rest arriving.
  28. Plan a lookup table by its account, not just its savings (Tool 31 above): a table is an account of 56 metadata bytes + 32 per stored address (256 maximum, because the indexes are u8) with a rent-exempt deposit to match — 2,104 bytes and 15,534,720 lamports for 64 addresses — and its per-transaction saving is the table reference (32-byte key, a list byte and two shortvec counts) plus 1 byte per loaded address against 32 bytes inline: one loaded address costs 4 bytes MORE through a table, twenty cost 55 bytes instead of 640. Deactivating and closing a table to reclaim the deposit waits out a cooldown first.
  29. Read an oracle price as a band, never a point (Tool 32 above): a Pyth-style feed publishes price ± conf at one exponent, conf being roughly one standard deviation — so judge a price by its band width in basis points of the price (150.00 ± 0.075 is 5 bps and passes a 1% guard; 67,890 ± 680 is 100.16 bps and fails that same guard), value collateral at the band's low end, and check staleness separately before trusting any of it.
  30. Price a launchpad token off its virtual reserves, not its vault (Tool 33 above): a bonding curve's price is virtual SOL ÷ virtual token on a constant-product curve — the virtual SOL is a pricing offset, while the SOL the curve actually holds is the real raised figure that counts toward graduation. Every buy moves the price along the curve (3 SOL into the headline curve receives 90,081,892.62966333 tokens and lifts the price 20.78%), and at graduation the real SOL and unsold tokens migrate to an AMM at a continuous price but with the virtual depth left behind.
  31. Price the funding before the leverage (Tool 34 above): a perpetual charges (or pays) funding every interval — payment = notional × rate × time, longs paying shorts at a positive rate and shorts paying longs at a negative one. A 100-unit long at 150 pays 1.5 per hour at just 1 bp per hour — 36 over a day — and that rate annualises to 87.6%, so a funding rate that looks like a rounding error is a real carry cost on any hold longer than a scalp; the rate resets every interval, which is why the annualised figure is a quote, never a forecast.
  32. Read a lending rate off its curve, not its headline (Tool 35 above): a borrow rate is a kinked function of utilization — borrowed ÷ supplied — climbing gently to the optimal utilization, then steeply past it, and suppliers earn the borrow rate × utilization × (1 − reserve factor). A market at exactly its 80% kink with a 2% base and 4% first slope charges 6% and pays suppliers 4.32%; the same market at 90% charges 36%. A quoted supply yield is only as durable as the utilization under it, and every parameter is governance-set, so check the curve before trusting either rate.
  33. Judge a perp by its liquidation price, not its leverage alone (Tool 36 above): equity = margin + PnL is liquidated when it falls to the maintenance margin — a venue-set rate times the current notional — so a 10x long at a 500 bps maintenance rate liquidates on a fall of only about 5.26%, while equity still remains; the same leverage multiplies your return on margin exactly, in both directions. Funding (Tool 34) is the carry on top of this, and no leverage at or below 1x has a liquidation price at all.
  34. Stable pools price off an invariant, not x × y = k (Tool 37 above): a stableswap pool's amplification coefficient holds the price near 1:1 while the pool stays balanced — a balanced 1,000,000 / 1,000,000 pool at A = 100 returns a 10,000 trade at 9,999.502463058, where constant-product returns 9,900 — but unbalance the pool and the same curve bends back toward constant-product pricing. The peg is defended by balanced liquidity, never guaranteed by the formula.
  35. Install Anchor from anchor-lang.com and run anchor init: you get a Rust program, an IDL and TypeScript tests in one scaffold.
  36. Read a real swap before writing one: run Tool 2 with a big amount in and watch price impact grow — that curve is what every AMM on Solana prices against.
  37. Test on devnet, then localnet: anchor test spins up a local validator; deploy to devnet only when tests pass. Never learn on mainnet with real funds.
  38. Ship and catalogue it: the full checklist lives in the getting-started guide in the repo.
